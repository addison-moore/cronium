- [2026-11-09] [Security] **A server's health check now gets only that server's answers, and SSH health checks and connection tests close their connections.** The app's SSH service is one object for the whole process, and it kept each call's connection on itself, so calls at the same moment, whoever made them, ran over and closed each other's connections. A health check that overlapped another could come back with the other server's kernel release, CPU count, memory and uptime, which a server's page shows, and the other check then failed. One that overlapped a connection test, which anyone signed in can run against any address, failed with `Cannot read properties of undefined (reading 'exec')`, and the server was marked offline. Each of those left a connection open on the server, kept alive with nothing to close it, and so did a health check whose command the server refused, or that overlapped a connection test that failed. Each call now has its own connection and closes it however it ends, and the messages are the same. Nothing else crossed over: each connection still signs in with its own server's credentials and checks its own host key, and a health check only runs its five fixed commands.
- [2026-11-09] [Security] **An SSH health check now gives up on a server that doesn't answer, and closing an SSH connection always closes its socket.** A health check waited with no limit for each of its five commands, so a server that took a command and never answered held `servers.checkHealth`, or a bulk health check, and its SSH connection for as long as the app ran, and anyone signed in can point a server at a host they control and check it again and again. The five commands now get 30 seconds together, after which the check closes its connection and reports the server offline with `Health check timed out: <address> didn't answer its commands within 30 seconds.` Closing a connection also said goodbye and then waited for the server to close its side, so a server that never did kept the socket open for good, after a health check, a connection test or a refused password alike. The socket now closes 5 seconds later if the server hasn't closed it. Every other message is the same.
- [2026-11-09] [Security] **A terminal's SSH connections now close their sockets too, whatever the server does.** The terminal keeps its SSH connections in a pool and closes them itself: one it has kept for 5 minutes, one that fails the check it runs before handing a connection out again, one whose shell the server refuses, and one with five shells, 5 seconds after a new connection replaces it. Each of those said goodbye and then waited for the server to close its side, so a server that never did kept the socket open for good, and so did a refused password, after which ssh2 says goodbye by itself. Anyone allowed to use the terminal can add a server at an address they control and open its terminal again and again. These sockets now close 5 seconds later if the server hasn't closed them, as a health check's and a connection test's already do. Closing a connection also took whatever the pool held for the same server and credentials out of the pool, so 5 seconds after a sixth terminal replaced a connection, at any server, the new connection fell out of the pool and stayed open with nothing to close it. Now a connection only takes itself out. Every message is the same.
- [2026-11-09] [Fix] **A terminal no longer closes while it's in use because its SSH connection has been open 5 minutes, or because more terminals opened to the same server.** The terminal keeps its SSH connections in a pool, and the pool closed a connection 5 minutes after it last handed it out, checking every 2 minutes, whether or not its shells were in use, so a terminal was cut 5 to 7 minutes after it opened unless another terminal to the same server opened meanwhile. A connection carries up to five shells, and when a sixth terminal opened, the pool moved on to a new connection and closed the old one 5 seconds later, which ended the first five terminals. It also closed a connection, shells and all, when the check it runs before handing a connection out again failed, or when the server refused a shell over it. A server that allows few sessions per connection, such as OpenSSH with `MaxSessions 1`, does both while a terminal is open, so opening a second terminal ended the first. The pool now counts each connection's open shells and closes a connection only once it has none: one it no longer hands out closes as soon as its last shell ends, and one it still hands out once it has had no shell for 5 minutes. Closing a terminal also took two shells off its connection's count, one when the terminal let the shell go and another when the shell closed, so the count could read zero with a terminal still open. It counts once now. Every message is the same.
