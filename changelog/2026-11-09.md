- [2026-11-09] [Fix] **An inbound webhook request that fails partway no longer leaves its event stored, never sent, and its delivery id used up.** The endpoint stored its own `webhook_events` row, then the row its deliveries go out from, as two separate writes. When the second failed, as it did every time for an event name of 248 to 255 characters at a webhook subscribed to `*`, the sender got a 500, the first row stayed, and sending it again under the same `X-Webhook-Delivery-Id` got `401 Duplicate or replayed delivery` with nothing sent. Both rows now go in one transaction, and the deliveries are queued only once it has committed, so a failure before the COMMIT leaves nothing and the id free to send it again. The id stays used only when the connection to Postgres is lost during the COMMIT, since Cronium can't tell then whether the event went in, and it queues nothing for it. What Postgres can never store now gets a 400 saying why, before anything is written, where it used to get a 500 on every attempt: an event name over 247 characters, a NUL character, or half of a UTF-16 surrogate pair, in the name, a key or a value.
