# 2026-11-09

- [2026-11-09] [Fix] **With Valkey down or full, sign-in and the other rate-limited endpoints now answer a 503 saying Cronium couldn't check its limit, not that there were too many attempts.** The atomic rate limiter refuses every request it can't count, on purpose, so brute force can't be unlocked by stopping Valkey, but it gave its callers the same answer as a reached limit. Measured on a production build with Valkey stopped (`docker stop`) and with Valkey refusing writes (`maxmemory 1` under the `noeviction` policy the compose file sets): MCP client registration answered `429 invalid_request` "Too many registration requests". Sign-in, account registration, forgot and reset password, the reset and invitation links, account activation and the MFA settings answered `429 TOO_MANY_REQUESTS` "Too many attempts. Please try again after" a time that meant nothing. NextAuth's sign-in answered "Too many login attempts", which the sign-in form showed as a wrong password, and a TOTP code whose use couldn't be recorded was called invalid. The limiter now says when it couldn't check. Every caller still refuses and nothing is counted, but the answer is a 503: `temporarily_unavailable` in OAuth's shape for registration, `SERVICE_UNAVAILABLE` on tRPC with "Cronium can't check its limit on attempts right now, usually because Valkey is down or full, so it didn't go ahead. Try again shortly.", and from NextAuth's sign-in a 503 with the code `RATE_LIMIT_UNAVAILABLE`, which the sign-in form and the auth error page show as that message. The same TOTP code works once Valkey is back. A real limit still gets the 429, or NextAuth's 401, it always had, word for word. **Not changed:** with Valkey stopped, each of these requests can still wait about 10 seconds for the limiter's reconnect attempts before it answers.
