# 2026-11-09

- [2026-11-09] [Fix] **A webhook sender is no longer told it's replaying while Cronium can't reach Valkey.** The inbound endpoint checks each `X-Webhook-Delivery-Id` in Valkey, and when it couldn't reach Valkey, or Valkey wouldn't store the id because it was full, it answered every signed request with `401 Duplicate or replayed delivery`. That reads as an attack and stops a sender retrying. It now answers `503` with `Retry-After: 30` and an error saying delivery ids can't be checked. It still accepts nothing it can't check, and the id isn't used, so the same request goes through once Valkey is back. An id used before the outage still gets its `401` after it. A new id got the same false `401` from a connection that dropped at the wrong moment, when Valkey had taken the id and its answer was lost, or the client sent the check again after reconnecting. Each request's check now holds a token of its own, so a check sent twice knows the id is its own, and one whose answer was lost is let go of when the next request under the id arrives. The same goes for a request refused after Valkey went away, which used to leave its id used for 11 minutes: it gets the answer it would have had, and its id works once Valkey is back. Only the process that answered knows this, so it's lost if that process restarts first or the next request goes to another replica. Letting go of an id also only removes the request's own claim now, so it can't free an id another request has taken since Valkey lost the first. `docs/WEBHOOKS.md` says what a sender sees, and `tests/storage/webhook-delivery-id-outage.test.ts` covers it through the real route, against real Postgres and a Valkey that goes away.
- [2026-11-09] [Fix] **A webhook sender now hears back within seconds when Valkey stops answering, instead of waiting for as long as it doesn't.** The inbound endpoint checks each `X-Webhook-Delivery-Id` in Valkey, and the client it uses had no limit on how long it waited for an answer. A Valkey that stopped answering with its connection left open, as a paused container or a network partition leaves it, held every signed request until it answered again: with the Valkey container under `docker pause`, a request had no answer after 15 seconds, then got its `200` once Valkey was unpaused. A request now waits at most 2 seconds, then gets the `503` with `Retry-After: 30` that an unreachable Valkey gives, with nothing stored. A paused Valkey still runs the check when it resumes, taking the id for a request that was told nothing happened, so the process remembers it and lets go of it when the next request under the id arrives, and the same id is accepted once Valkey answers. Once one request has given up, nothing more is sent until Valkey answers, and the requests after it get the `503` at once, so a long pause doesn't leave a queued command and a remembered id behind for every request. Letting go of a refused request's id waits no longer, and a process remembers at most 10,000 ids it couldn't let go of, forgetting the oldest. `docs/WEBHOOKS.md` says what a sender sees, and `tests/storage/webhook-delivery-id-outage.test.ts` pauses Valkey through the real route.
