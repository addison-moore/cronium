# 2026-11-09

- [2026-11-09] [Security] **A server's health check now gets only that server's answers, and SSH health checks and connection tests close their connections.** The app's SSH service is one object for the whole process, and it kept each call's connection on itself, so calls at the same moment, whoever made them, ran over and closed each other's connections. A health check that overlapped another could come back with the other server's kernel release, CPU count, memory and uptime, which a server's page shows, and the other check then failed. One that overlapped a connection test, which anyone signed in can run against any address, failed with `Cannot read properties of undefined (reading 'exec')`, and the server was marked offline. Each of those left a connection open on the server, kept alive with nothing to close it, and so did a health check whose command the server refused, or that overlapped a connection test that failed. Each call now has its own connection and closes it however it ends, and the messages are the same. Nothing else crossed over: each connection still signs in with its own server's credentials and checks its own host key, and a health check only runs its five fixed commands.
- [2026-11-09] [Security] **An Email credential with Enable TLS ticked no longer signs in or sends without TLS.** Nothing read the box, which is ticked by default. A send and Test connection used STARTTLS only when the server listed it, so a server without TLS got the SMTP password and the whole message in plaintext, and so did anyone between Cronium and the server who removed STARTTLS from that list. Measured against Mailpit: a relay that removed `250-STARTTLS` from the answer of a server offering TLS read `AUTH PLAIN` with the password, and the message, from both. A ticked box now asks for STARTTLS whether or not it's listed, and ends the session before signing in if the server refuses it or the upgrade fails. Through the same relay, the session switched to TLS and the email arrived. Enable SSL, which is TLS from the first byte on port 465, is unchanged, and with it ticked the TLS box has nothing to add. Unticked, Enable TLS works as it did: STARTTLS when the server offers it, plaintext when it doesn't. **Upgrade:** a credential pointed at a server without STARTTLS, such as a local relay on port 25 or a mail catcher like Mailpit or MailHog, now fails every send, Test connection and Check Login with `<host> didn't switch to TLS when asked (STARTTLS), so Cronium didn't sign in or send anything. To use this server without encryption, untick Enable TLS on this credential.`, followed by what the server answered, and a run's output starts `The mail server didn't switch to TLS`. To find such credentials before a run fails, press Test on each Email credential on the Tools page. Untick Enable TLS on any that should go on sending unencrypted.
- [2026-11-09] [Feature] **The event form now offers a check beside the real run for MongoDB Update and Delete, Email and Discord, which changes and sends nothing.** `Count Matches` counts the documents the filter matches, with the real run's own collection and filter revived the same way, and says when only the first would be touched or Upsert would add one. `Check Login` connects and signs in to the mail server exactly as a send would, then leaves before naming a sender or a recipient. It says so when the server never asked for a login, and it doesn't reuse the credential test, which accepts any certificate where the send doesn't. `Check Webhook` asks Discord for the webhook with a GET and passes back only its name, because Discord's answer carries the webhook's token. Each toast says what the check showed and then what it didn't: a login isn't a delivered email, and a count doesn't show the delete would be allowed. The real run still asks first, and its question no longer says there's no test mode. Measured in a production build on throwaway MongoDB and mail servers, with no route out but loopback: no check changed a document or sent a message, and a wrong password or an unknown webhook failed the check as it fails the real run. `countDocuments` refuses `$where`, which a delete accepts, so that check fails and says why. The form now says which it wants, `check`, `simulate` or `run`, and the server refuses a check or a simulation of an action that doesn't declare one, so neither can become a real run. A page loaded before this sends only `isTest`, and still gets the real run its button promised. A check is audited as `CHECKED`. SQL Execute Statement, Slack, Teams, Notion, Trello and Google Sheets get no check: a rollback isn't safe on MySQL, Slack and Teams have no call without an effect, and the rest can't be checked here without real accounts.
- [2026-11-09] [Feature] **The event form now shows what a run from its button returned, under the button.** Pressing `Run Query Now`, `Find Documents Now`, `Aggregate Documents Now` or `Prompt LLM Now` really runs the action, but the rows, the documents and the model's answer only went to the browser console, so someone who paid for a prompt couldn't read the answer. Rows now show as a table, documents as JSON, and an answer as written, with the model, the tokens it used, and a warning when it stopped at Max Tokens. A read can return up to 5 MB, so the form draws the first 100 rows or documents and 200,000 characters at most, cuts a value at 200 characters and a document at 5,000, and says what it left out. The result goes when the credential or action changes, by a choice or through the event's settings, and when the button is pressed again, and one that comes back after the action was changed isn't shown. A parameter edit keeps it and says it's from before, so a paid answer isn't lost to an edit. A simulation shows nothing, since its result is made up, such as Google Sheets' "Product A", and neither does a send or a write, which comes back with little more than the count the toast gives. Each action declares what's shown in `testRun.shows`, which the type requires of a read or a prompt and refuses for the rest. The result no longer goes to the console.
- [2026-11-09] [Security] **An SSH health check now gives up on a server that doesn't answer, and closing an SSH connection always closes its socket.** A health check waited with no limit for each of its five commands, so a server that took a command and never answered held `servers.checkHealth`, or a bulk health check, and its SSH connection for as long as the app ran, and anyone signed in can point a server at a host they control and check it again and again. The five commands now get 30 seconds together, after which the check closes its connection and reports the server offline with `Health check timed out: <address> didn't answer its commands within 30 seconds.` Closing a connection also said goodbye and then waited for the server to close its side, so a server that never did kept the socket open for good, after a health check, a connection test or a refused password alike. The socket now closes 5 seconds later if the server hasn't closed it. Every other message is the same.
- [2026-11-09] [Fix] **A Valkey outage no longer costs an MCP OAuth client its refresh token, and a full Valkey no longer hands out one it never stored.** MCP OAuth's clients, codes and refresh tokens live only in Valkey, and the cache's reads answer null both for a key that isn't there and for a Valkey they couldn't ask. Measured on a production build: with Valkey stopped, a good refresh token got `400 invalid_grant`, and the MCP SDK answers that by throwing its tokens away, so the client's owner had to authorize it again, though the same token worked once Valkey was back. A code got `invalid_grant` too, and the consent page called a registered client unknown. With Valkey refusing writes, as it does at its `maxmemory` under the `noeviction` policy the compose file sets, a refresh answered 200 with a new refresh token that was never stored, after taking the old one, so the next refresh got `invalid_grant`. A code exchange did the same, and the consent page sent the client a code it never stored. The OAuth server now reads and writes Valkey through new strict cache methods, so a Valkey it can't ask gets the 503 with `temporarily_unavailable` that a database outage gets, the token stays where it was, and the same token works once Valkey is back. The token endpoint stores the new refresh token before it takes the old one, so a refused write leaves the client the token it has, and a request that loses the race to another takes its own new one off again. The consent page now says it couldn't look the application up, an approval it can't store sends the client back with `temporarily_unavailable` rather than a code, and registration answers a 503 rather than a `client_id` it didn't store. A code or refresh token that really isn't there still gets `invalid_grant`, and single use hasn't changed: 30 requests at once with one token, over two processes, still let exactly one through, and a replay after a success is still refused. **A process that had just started** also answered its first OAuth requests with `invalid_grant`, because its cache was still connecting when they arrived: all 5 refreshes sent to a freshly restarted process were refused, and worked when sent again. The strict reads now wait for that first connection, and all 5 got tokens. **Also fixed, for every user of the cache:** an app that started while Valkey was down kept its cache off until it restarted, every read a miss and every write refused, while the health check said the cache was available. It now comes on once Valkey does. The cache's other methods still answer a key Valkey couldn't be asked about as a miss, as before.
- [2026-11-09] [Fix] **A webhook sender is no longer told it's replaying while Cronium can't reach Valkey.** The inbound endpoint checks each `X-Webhook-Delivery-Id` in Valkey, and when it couldn't reach Valkey, or Valkey wouldn't store the id because it was full, it answered every signed request with `401 Duplicate or replayed delivery`. That reads as an attack and stops a sender retrying. It now answers `503` with `Retry-After: 30` and an error saying delivery ids can't be checked. It still accepts nothing it can't check, and the id isn't used, so the same request goes through once Valkey is back. An id used before the outage still gets its `401` after it. A new id got the same false `401` from a connection that dropped at the wrong moment, when Valkey had taken the id and its answer was lost, or the client sent the check again after reconnecting. Each request's check now holds a token of its own, so a check sent twice knows the id is its own, and one whose answer was lost is let go of when the next request under the id arrives. The same goes for a request refused after Valkey went away, which used to leave its id used for 11 minutes: it gets the answer it would have had, and its id works once Valkey is back. Only the process that answered knows this, so it's lost if that process restarts first or the next request goes to another replica. Letting go of an id also only removes the request's own claim now, so it can't free an id another request has taken since Valkey lost the first. `docs/WEBHOOKS.md` says what a sender sees, and `tests/storage/webhook-delivery-id-outage.test.ts` covers it through the real route, against real Postgres and a Valkey that goes away.
- [2026-11-09] [Fix] **An inbound webhook request that fails partway no longer leaves its event stored, never sent, and its delivery id used up.** The endpoint stored its own `webhook_events` row, then the row its deliveries go out from, as two separate writes. When the second failed, as it did every time for an event name of 248 to 255 characters at a webhook subscribed to `*`, the sender got a 500, the first row stayed, and sending it again under the same `X-Webhook-Delivery-Id` got `401 Duplicate or replayed delivery` with nothing sent. Both rows now go in one transaction, and the deliveries are queued only once it has committed, so a failure before the COMMIT leaves nothing and the id free to send it again. The id stays used only when the connection to Postgres is lost during the COMMIT, since Cronium can't tell then whether the event went in, and it queues nothing for it. What Postgres can never store now gets a 400 saying why, before anything is written, where it used to get a 500 on every attempt: an event name over 247 characters, a NUL character, or half of a UTF-16 surrogate pair, in the name, a key or a value.
- [2026-11-09] [Security] **One signed-in user can no longer open thousands of connections at once to hosts they typed, or use Cronium as a fast port scanner.** Testing, adding or re-keying a server, a server's health check, alone or through `servers.bulkOperation`, `POST /api/servers`, `PUT /api/servers/[id]`, and testing a tool through `tools.testConnection` or `tools.testCredentials` each connect to wherever the user typed, and nothing limited them. `withRateLimit` reads then writes, so it doesn't stop calls made at the same moment. Measured through the real routes with real Postgres and Valkey: 5,000 `servers.testConnection` calls at once at a server that never answers held 5,000 sockets for `ssh2`'s 60 seconds, and with a limit of 1,024 open files about 3,900 of them failed with `EMFILE`. One user calling in 8 loops reached a closed port 269,563 times in a minute, and each answer says whether something listens there. Each user now gets 8 of these at once in each app process. Up to 64 more wait their turn, in order, for up to 15 seconds, and past that a call is refused at once. At most 60 start a minute for each user, counted atomically in Valkey, so calls made at the same moment can't get past it, and every app process shares the count. A refusal is a `TOO_MANY_REQUESTS` error, or a 429 from the REST routes with `Retry-After` for the minute, that says which limit was reached. It comes before anything connects or is written, so it can't mark a server offline, and the Tools page shows a refused tool as not checked, with the reason in its tooltip, rather than broken. Its badges also show that a check is under way. **When Valkey doesn't answer** within 2 seconds, each process counts by itself, says so once in the log, and asks Valkey again 10 seconds later, rather than refusing every server and tool check as sign-in does. With more than one app process, a user can start 60 a minute in each while that lasts. **What changes:** opening the Tools page tests every tool it lists in one request, so a page of more than 8 tools at hosts that don't answer takes longer: 20 SQL tools whose server never answers took 20 seconds to show, where they took 10, and 4 of them showed as not checked. 20 that answer took under a tenth of a second either way. A user who reaches 60 in a minute, for example with many tools and the page opened several times, sees the rest as not checked until the minute is up. The count is in fixed windows, so a minute that spans two can see up to 120. A check that never finishes keeps its turn: every connection here has a time limit, but a server's health check commands don't once it's connected, so a server that answers keep-alives and never finishes a command keeps one of its owner's 8 turns until the app restarts.
