# 2026-11-09

- [2026-11-09] [Fix] **A Valkey outage no longer costs an MCP OAuth client its refresh token, and a full Valkey no longer hands out one it never stored.** MCP OAuth's clients, codes and refresh tokens live only in Valkey, and the cache's reads answer null both for a key that isn't there and for a Valkey they couldn't ask. Measured on a production build: with Valkey stopped, a good refresh token got `400 invalid_grant`, and the MCP SDK answers that by throwing its tokens away, so the client's owner had to authorize it again, though the same token worked once Valkey was back. A code got `invalid_grant` too, and the consent page called a registered client unknown. With Valkey refusing writes, as it does at its `maxmemory` under the `noeviction` policy the compose file sets, a refresh answered 200 with a new refresh token that was never stored, after taking the old one, so the next refresh got `invalid_grant`. A code exchange did the same, and the consent page sent the client a code it never stored. The OAuth server now reads and writes Valkey through new strict cache methods, so a Valkey it can't ask gets the 503 with `temporarily_unavailable` that a database outage gets, the token stays where it was, and the same token works once Valkey is back. The token endpoint stores the new refresh token before it takes the old one, so a refused write leaves the client the token it has, and a request that loses the race to another takes its own new one off again. The consent page now says it couldn't look the application up, an approval it can't store sends the client back with `temporarily_unavailable` rather than a code, and registration answers a 503 rather than a `client_id` it didn't store. A code or refresh token that really isn't there still gets `invalid_grant`, and single use hasn't changed: 30 requests at once with one token, over two processes, still let exactly one through, and a replay after a success is still refused. **A process that had just started** also answered its first OAuth requests with `invalid_grant`, because its cache was still connecting when they arrived: all 5 refreshes sent to a freshly restarted process were refused, and worked when sent again. The strict reads now wait for that first connection, and all 5 got tokens. **Also fixed, for every user of the cache:** an app that started while Valkey was down kept its cache off until it restarted, every read a miss and every write refused, while the health check said the cache was available. It now comes on once Valkey does. The cache's other methods still answer a key Valkey couldn't be asked about as a miss, as before.
