- [2026-07-25] [Bug Fix] **Container jobs could not use any `cronium.*` helper — every call got 401 since revoke-on-terminal (HI-14) shipped.** The orchestrator's container lineage minted the execution-JWT job-id claim as `job_id` ("backward compatibility") while the runtime — and the orchestrator's own SSH lineage — read `jobId`; the runtime's fail-closed RevocationMiddleware rejects an empty JobID, so `cronium_output`/`cronium.input()`/variables from container jobs uniformly 401'd (plain scripts don't call the runtime, which is why nothing noticed). Caught by the new Phase 5 e2e workflow scenario on its first run. Fixed on both sides: the container lineage now mints `jobId` (matching SSH + runtime), and the runtime additionally accepts legacy `job_id` so older orchestrator images keep working across image skew (regression test in `internal/auth/jwt_test.go`). Also fixed alongside: the bash SDK swallowed the failure detail (parsed only `.message`; the runtime sends `{"error":...}`) — errors now read `HTTP <code> - <message|error>` (canonical + container-image mirrors synced).
