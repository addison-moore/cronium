# 2026-11-06

- [2026-11-06] [Security] **The worker, the socket server and the services in `lib/` no longer put what a failed query was saving in the server log.** Measured against real Postgres, a scheduled event whose job couldn't be saved logged the job's payload: its script, an HTTP event's URL, headers and body, its input, and its env vars as stored, so in plaintext on a row not yet encrypted. A failed workflow advance logged a step's output, and a retry that couldn't be recorded logged what the job printed. They now log the SQLSTATE and Postgres's own message, and keep their stack frames, like the REST routes. Some of that text was also stored, in plaintext, where a run's owner can read it: `workflow_step_runs.error`, `workflow_execution_events.error_message`, `schedule_incidents.details`, and a job's log when saving its result failed. Those now hold `A database query failed`, and so do the error sent to a client asking for a terminal and the error from saving OAuth tokens, which a redirect's query string carries. Also closed: a cache write Valkey refused logged the value being cached, stored tool credentials that aren't valid JSON reached the log and the job's output through `JSON.parse`'s message, a rejected job transition logged its reason, which can be what a script printed, and `bootstrap-seed.cjs` logged the first admin's email and password hash when an insert failed. Lint now fails on logging a caught error directly across this code. **Existing logs and rows can still hold these values**: treat older logs as sensitive, search those columns for `Failed query`, and rotate any credential saved in an event around a failed dispatch. `tests/storage/query-failure-logging.test.ts` covers this against real Postgres.
- [2026-11-06] [Fix] **A `bash` that a container job's script starts can now call the `cronium_*` helpers.** It inherited the functions but not the shell variables they read, so every call failed with `Error: Max retries exceeded` before making a request. They now read `CRONIUM_RUNTIME_API`, `CRONIUM_EXECUTION_TOKEN` and `CRONIUM_EXECUTION_ID` each time they run, and a script can use `MAX_RETRIES` and `RETRY_DELAY` itself, which used to break its helper calls. The bash runner image no longer sets `BASH_ENV`: it named a file the `/home` tmpfs hides, so it did nothing in a job. **Upgrade:** rebuild `cronium/runner:bash-alpine`. A script that unsets `CRONIUM_RUNTIME_API` or `CRONIUM_EXECUTION_ID` can no longer call helpers, and changing `CRONIUM_API` or `CRONIUM_EXEC_ID` no longer redirects them.
