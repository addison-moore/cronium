# 2026-11-06

- [2026-11-06] [Fix] **A `bash` that a container job's script starts can now call the `cronium_*` helpers.** It inherited the functions but not the shell variables they read, so every call failed with `Error: Max retries exceeded` before making a request. They now read `CRONIUM_RUNTIME_API`, `CRONIUM_EXECUTION_TOKEN` and `CRONIUM_EXECUTION_ID` each time they run, and a script can use `MAX_RETRIES` and `RETRY_DELAY` itself, which used to break its helper calls. The bash runner image no longer sets `BASH_ENV`: it named a file the `/home` tmpfs hides, so it did nothing in a job. **Upgrade:** rebuild `cronium/runner:bash-alpine`. A script that unsets `CRONIUM_RUNTIME_API` or `CRONIUM_EXECUTION_ID` can no longer call helpers, and changing `CRONIUM_API` or `CRONIUM_EXEC_ID` no longer redirects them.
- [2026-11-06] [Fix] Restarting the orchestrator no longer abandons the jobs it was running. Any recreate, which meant any `.env` change and every upgrade, left the job's script running with nothing watching it: its result was lost, the sweeper failed or re-ran the job about 90 seconds later, and its sidecar and network stayed until removed by hand. Now a container job carries on through the restart. On SIGTERM the orchestrator exits at once and leaves running containers in place, and its next process finds them by label before it claims anything, renews their leases, follows them to the end and reports them, including a script that ended while no orchestrator was running. A job whose lease is gone has been failed or re-queued, so its containers are removed, killing the script if it's still going. The job's containers now stay until its result has been reported or spooled, so a process killed at any point leaves the next one something to work from. A job's next attempt also clears whatever its last one left, which previously failed it on a name conflict.
- [2026-11-06] [Fix] The orchestrator no longer waits 30 seconds for jobs it can leave running. A recreate stops the app first and starts nothing until the orchestrator has stopped, so that wait took the whole stack down for longer and used up the lease that lets the next process pick the job up. It now waits only for what can't be left, which is remote jobs and jobs still starting, then stops those and leaves them to the sweeper instead of reporting them cancelled. All compose files give it `stop_grace_period: 40s` for this. Completions spooled by the previous process are delivered on start instead of a minute later.
- [2026-11-06] [Fix] A worker that just started waits one lease length before its first sweep. An orchestrator renews leases through the app, so a lease that ran out while a restarting stack had the app down says nothing about its owner, and the worker starts before the orchestrator. A slow restart used to fail a healthy job just before its owner could renew it.
- [2026-11-06] [Fix] `docker-compose.example.yml` no longer gives `cronium-orchestrator` and `cronium-runtime` all of `.env`. Any `.env` change recreated them, cutting off remote jobs, and handed them `ENCRYPTION_KEY`, `AUTH_SECRET` and the rest for no reason. Common orchestrator settings are listed by name and still come from `.env`, and a test checks that each is one the orchestrator reads. **If you set another `CRONIUM_*` value in `.env`, it no longer reaches the orchestrator: add its name to that service's `environment`.**
- [2026-11-06] [Fix] A failed wait on a job's container no longer counts as exit code 0. Losing the connection to Docker reported the job as completed, and a cancelled or timed-out job could land the same way if the wait broke first. The exit code now comes from Docker, and the job fails if Docker can't say.
- [2026-11-06] [Fix] The orchestrator's periodic cleanup now finds sidecars, which it looked for under a name they never had, and leaves alone containers belonging to another orchestrator or stack on the same Docker host. Job containers now carry the `cronium.managed` label that sidecars and networks already had, along with the orchestrator ID and stack. `install.sh --uninstall` removes what's left of running jobs, since nothing will come back for them.
