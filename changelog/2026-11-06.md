# 2026-11-06

- [2026-11-06] [Fix] **A `bash` that a container job's script starts can now call the `cronium_*` helpers.** It inherited the functions but not the shell variables they read, so every call failed with `Error: Max retries exceeded` before making a request. They now read `CRONIUM_RUNTIME_API`, `CRONIUM_EXECUTION_TOKEN` and `CRONIUM_EXECUTION_ID` each time they run, and a script can use `MAX_RETRIES` and `RETRY_DELAY` itself, which used to break its helper calls. The bash runner image no longer sets `BASH_ENV`: it named a file the `/home` tmpfs hides, so it did nothing in a job. **Upgrade:** rebuild `cronium/runner:bash-alpine`. A script that unsets `CRONIUM_RUNTIME_API` or `CRONIUM_EXECUTION_ID` can no longer call helpers, and changing `CRONIUM_API` or `CRONIUM_EXEC_ID` no longer redirects them.
- [2026-11-06] [Fix] **One job going wrong during a claim now costs only that job.** `POST /api/internal/jobs/claim` answered 500 for the whole batch when failing a job it couldn't prepare threw, for example because the job's log row was gone. The rest of the batch stayed claimed and undelivered, and when their leases ran out the sweeper failed them without running them, or spent one of their retries, while the orchestrator's retry of the 500 claimed another batch. The route now answers 200 with what it could deliver. `updateJobStatus` treats a missing log as nothing to write rather than an error, so status, completion and failure reports on such a job answer 200 and aren't retried and spooled, and a tool action or HTTP job in the same position runs instead of being failed. It also records why a job ended on `jobs.last_error`, up to 4,000 characters, in the same transaction as the status, which the job page and a failed workflow step read. A log write that fails with the log still there still answers 500, so a reporter retries it. `/status` now reads the message out of the error object the orchestrator sends when a job can't start, instead of storing its JSON.
