# 2026-11-06

- [2026-11-06] [Fix] **Duplicate works on events with servers, and a server's page lists its events.** Duplicate sent an event's server links under a name `events.create` ignores, so it couldn't copy a `REMOTE` event linked through `event_servers`, and it left out a tool action's config, so it couldn't copy those either. It now sends both. **An archived server stops a copy, as it does a fork:** no draft is made, and the refusal names the server. A new copy or fork also appears in the list without a reload. `servers.getEvents` failed on every call against real Postgres, `column events.event_id does not exist`, and the server's page showed that as "No events configured to run on this server yet." It now lists them. On that page, Duplicate copies the links, the server column shows the event's servers, not `local`, and Fork really forks, where it used to run Duplicate on data with the owner's servers removed. The events list also no longer marks every row as someone else's until the viewer has loaded: rows show no share icon and only View Details until the session answers, and a failed `getCurrentUser` no longer leaves them that way.
- [2026-11-06] [Fix] **A webhook event past 1 MB now reaches its receivers.** A delivery's request was limited by the constant meant for its response, so axios refused any body past 1 MB before sending it, and the queue repeated that until its retries ran out: no requests, and three failed rows. The inbound endpoint takes bodies up to 1 MB and escaping can make them up to 6 times as long, so a request of 300 KB could be answered with a success and its event never go out. A delivery now has its own limit of 8 MB, which holds anything the endpoint accepts. An event past that gets one failed row and no retries through the queue. `webhookSystem.test` and `webhookSystem.retryDelivery` refuse one with `PRECONDITION_FAILED`, and the endpoint answers 413 and stores nothing, which takes a webhook with `transformations` that copy fields. Deliveries that failed this way can now be sent with a manual retry, and every other failure is retried as before.
- [2026-11-06] [Security] **A failed query's SQL and bound values no longer go back to whoever made the request.** Several places sent an error's message back as it was, and since drizzle-orm 0.44 that message is the whole statement and every value in it. The bulk operations on variables, logs, workflows, servers and users, the admin test email and the database health check returned it in a 200, which the production error formatter doesn't touch, so an admin resending an invite could read the new token's hash. MCP tool results put it in front of a model, because `createCaller` skips that formatter, and the OAuth callback put it in the `details=` query string of a redirect, with the encrypted tokens it was saving, where browser history and proxy logs keep it. These now say `A database query failed`, and the reason goes to the server log without the values, since the caller no longer gets it. The text of any other error is unchanged. On MCP, a procedure that chose its own message for a failed query, such as `Failed to fetch event`, now gives this line as well. `tests/storage/query-failure-responses.test.ts` covers this against real Postgres.
- [2026-11-06] [Fix] **The app now says when something other than Cronium answers it, and names the status.** The tRPC client parses a response before it looks at the status, so behind a proxy a 502 while Cronium restarted read `Unexpected token '<', "<html>..." is not valid JSON`, in a save's toast and on pages such as the dashboard. A 503, a 504, a firewall's 403 and an SSO proxy's sign-in page at 403 or 200 went the same way, Caddy's empty 502 and Traefik's plain text gave other parse errors, and a gateway's JSON, at any status, read `Unable to transform response from server`. These now read `Got HTTP 502, not Cronium's answer` with possible causes, and a save at a 5xx adds that it may still have gone through, because a real nginx 504 came back with the event saved. A sign-in proxy's redirect, which the browser followed into the app's own CSP and reported as `Failed to fetch`, reads `Got a redirect, not Cronium's answer.` The client tells Cronium's answers from others by the body, which it reads once, as it did before, so Cronium's own errors read as they did at every status, and retries and refetches are unchanged. `docs/DEPLOYMENT.md` now says a web application firewall needs an exception: ModSecurity with the OWASP Core Rule Set refuses ordinary scripts by default, and any request over 128 KB.
- [2026-11-06] [Fix] **A `bash` that a container job's script starts can now call the `cronium_*` helpers.** It inherited the functions but not the shell variables they read, so every call failed with `Error: Max retries exceeded` before making a request. They now read `CRONIUM_RUNTIME_API`, `CRONIUM_EXECUTION_TOKEN` and `CRONIUM_EXECUTION_ID` each time they run, and a script can use `MAX_RETRIES` and `RETRY_DELAY` itself, which used to break its helper calls. The bash runner image no longer sets `BASH_ENV`: it named a file the `/home` tmpfs hides, so it did nothing in a job. **Upgrade:** rebuild `cronium/runner:bash-alpine`. A script that unsets `CRONIUM_RUNTIME_API` or `CRONIUM_EXECUTION_ID` can no longer call helpers, and changing `CRONIUM_API` or `CRONIUM_EXEC_ID` no longer redirects them.
- [2026-11-06] [Test] `tests/storage/run-migrations.test.ts` no longer force-drops its databases, and its pools no longer ignore connection errors. The force-drop was what terminated sessions still closing, and the listener added to stop that failing at random also hid real failures: a session killed partway through a test passed. A plain `DROP DATABASE` waits for those sessions instead, so a session lost during a test now fails that test, and one left open when the file ends fails the file with `database is being accessed by other users`.
- [2026-11-06] [Fix] On Node 24, a request refused for its declared length no longer has its body read first. `withBodyLimit` refused it by piping the body into a stream that had already failed. Node 22's pipe stops there. Node 24's reads up to two chunks first and then destroys the request stream, and `request-body.test.ts` failed on every run on that version. The body is now cancelled unread, with no pipe. A client gets the same 413 either way, and CI and the Docker image use Node 22, so production wasn't affected.
- [2026-11-06] [Fix] **The bash SDK no longer overwrites an event's env vars named `CRONIUM_TOKEN`, `CRONIUM_API`, `CRONIUM_EXEC_ID` or `cmd` when it loads.** A container job given `CRONIUM_TOKEN` to call the REST API sent its execution token instead and got a 401. The new value also reached everything the script ran, so `env -u CRONIUM_EXECUTION_TOKEN tool` left the execution token in `tool`'s `CRONIUM_TOKEN`. **Upgrade:** rebuild `cronium/runner:bash-alpine`. The SDK no longer sets those three names, and leaves no `cmd` behind. A script that read them without defining them now gets an empty value, or an `unbound variable` error under `set -u`: read `CRONIUM_EXECUTION_TOKEN`, `CRONIUM_RUNTIME_API` and `CRONIUM_EXECUTION_ID` instead.
- [2026-11-06] [Fix] **Saving an event set up with a direct `serverId` no longer moves its script.** An event whose server was set through the deprecated `serverId` field, which the REST API, MCP and JSON import can all write, showed that server unticked in the event form. Any save then made a `LOCAL_AND_REMOTE` event `LOCAL` and cleared the server, and a `REMOTE` one answered `Select at least one execution location` until someone picked the server again. The server is now ticked, and a save moves it to the event's list of servers and clears `serverId`. A `LOCAL` event's leftover `serverId` stays unticked, because ticking it would add a server, and any save clears it as before. An event with both `serverId` and links ticks only where a run really goes, so an untouched save doesn't start or stop running it anywhere: with two or more links, or one on a `LOCAL_AND_REMOTE` event, a run skips `serverId`, and on a `REMOTE` event with one link a run skips that link. Whatever isn't ticked is dropped by the save. **One thing does start:** a `LOCAL_AND_REMOTE` event on `serverId` alone has only ever run on the server, because a run reaches its local half through links, so the first save from the form starts the local half too. That's what the event and the events list already said it did. `tests/storage/event-save-direct-server.test.ts` covers all of this against real Postgres and real job preparation.
- [2026-11-06] [Fix] **One job going wrong during a claim now costs only that job.** `POST /api/internal/jobs/claim` answered 500 for the whole batch when failing a job it couldn't prepare threw, for example because the job's log row was gone. The rest of the batch stayed claimed and undelivered, and when their leases ran out the sweeper failed them without running them, or spent one of their retries, while the orchestrator's retry of the 500 claimed another batch. The route now answers 200 with what it could deliver. `updateJobStatus` treats a missing log as nothing to write rather than an error, so status, completion and failure reports on such a job answer 200 and aren't retried and spooled, and a tool action or HTTP job in the same position runs instead of being failed. It also records why a job ended on `jobs.last_error`, up to 4,000 characters, in the same transaction as the status, which the job page, now opening a long one at its end, and a failed workflow step read. A log write that fails with the log still there still answers 500, so a reporter retries it. `/status` now reads the message out of the error object the orchestrator sends when a job can't start, instead of storing its JSON.
- [2026-11-06] [Fix] **Saving an event no longer moves its start time.** The form showed the stored time in UTC and read it back as the browser's local time, so each save moved it by the browser's offset, on the Edit tab, on `/dashboard/events/<id>/edit` and in a workflow's edit modal. At UTC-8, `05:06Z` became `13:06Z` after one save and `21:06Z` after two, and the event's first run moved with it. The field now shows the browser's local time and says which timezone that is, which is also how it has always read a time you type. The event's Timezone setting still applies only to cron schedules. A save that leaves the field alone keeps the stored time exactly, including seconds set through the API, which it used to drop, and a time in the hour the clocks repeat. **Start times already moved this way aren't restored**, so check any event with a start time that was saved from a browser not on UTC.
- [2026-11-06] [Fix] **Saving an event no longer leaves its old values in the browser's cache, where the next save could write them back.** `events.update` left the cached `events.getById` copy alone, so for a minute the workflow edit modal reopened with every field as it was before the save, and saving it put those values back. After a minute it also refetched, but the form reads most fields only when it mounts, so the name, script, status and schedule stayed old while variables, tags, servers and HTTP fields turned new, and a save stored that mix. The popover keeps the modal's query mounted, so this lasted as long as the workflow page stayed open, not until the 5-minute `gcTime`. The app's `QueryClient` now updates that copy after every `events.update`, `events.activate`, `events.deactivate` and `events.resetCounter`, wherever they're called from, which also stops a status set from the events list being undone by the next save from the event page's Edit tab. The modal also reads the event on each opening and holds the form until the answer is in, so another tab's save shows too, and a failed read shows an error with a Close button rather than an old copy to save.
- [2026-11-06] [Fix] **Actions on every other screen now say when they fail.** On the event page, a server's page and the servers list, the admin page, a workflow's webhook key, and the Slack and Google Sheets tools, a refused action showed nothing. The toast gives the server's reason, and a failed validation on the event form or the JSON dialog gives sentences instead of raw JSON. Three things said it worked when it hadn't: Approve and Deny on the admin page, and Slack's Test Connection when the webhook refused the test. A refused invite no longer closes the dialog and loses the address, and Slack's buttons no longer stay stuck on "Testing...". The health check a server's page runs when it loads stays quiet, because it's refused on every view of a shared or archived server.
- [2026-11-06] [Fix] **One webhook or tenant can no longer hold up everyone else's webhook deliveries.** The queue ran five deliveries at a time per process, oldest first, so five events to a receiver that never answers made another tenant's delivery wait 30 seconds, 20 events made it wait two minutes, and retries repeated it. A webhook can now have 5 deliveries running, a tenant 10 and the process 40, and a slot that comes free goes to the tenant, then the webhook, with the fewest running. Those waits are now milliseconds, and if all 40 slots are held, the next delivery waits for the first one to end. A backlog at a healthy receiver no longer holds up anyone else either: 60 events made another tenant wait 55 seconds, and now under a second. The backlog itself still goes out at about one request a second per webhook, because a receiver that limits its rate refuses anything faster.
