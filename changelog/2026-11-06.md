# 2026-11-06

- [2026-11-06] [Security] **The worker, the socket server and the services in `lib/` no longer put what a failed query was saving in the server log.** Measured against real Postgres, a scheduled event whose job couldn't be saved logged the job's payload: its script, an HTTP event's URL, headers and body, its input, and its env vars as stored, so in plaintext on a row not yet encrypted. A failed workflow advance logged a step's output, and a retry that couldn't be recorded logged what the job printed. They now log the SQLSTATE and Postgres's own message, and keep their stack frames, like the REST routes. Some of that text was also stored, in plaintext, where a run's owner can read it: `workflow_step_runs.error`, `workflow_execution_events.error_message`, `schedule_incidents.details`, and a job's log when saving its result failed. Those now hold `A database query failed`, and so do the error sent to a client asking for a terminal and the error from saving OAuth tokens, which a redirect's query string carries. Also closed: a cache error logged its whole key, which for MCP OAuth holds a live authorization code or a refresh token's id, a cache write Valkey refused logged the value being cached, stored tool credentials that aren't valid JSON reached the log and the job's output through `JSON.parse`'s message, a rejected job transition logged its reason, which can be what a script printed, and `bootstrap-seed.cjs` logged the first admin's email and password hash when an insert failed. Lint now fails on logging a caught error directly across this code. **Existing logs and rows can still hold these values**: treat older logs as sensitive, search those columns for `Failed query`, and rotate any credential saved in an event around a failed dispatch. `tests/storage/query-failure-logging.test.ts` covers this against real Postgres.
- [2026-11-06] [Fix] **Duplicate works on events with servers, and a server's page lists its events.** Duplicate sent an event's server links under a name `events.create` ignores, so it couldn't copy a `REMOTE` event linked through `event_servers`, and it left out a tool action's config, so it couldn't copy those either. It now sends both. **An archived server stops a copy, as it does a fork:** no draft is made, and the refusal names the server. A new copy or fork also appears in the list without a reload. `servers.getEvents` failed on every call against real Postgres, `column events.event_id does not exist`, and the server's page showed that as "No events configured to run on this server yet." It now lists them. On that page, Duplicate copies the links, the server column shows the event's servers, not `local`, and Fork really forks, where it used to run Duplicate on data with the owner's servers removed. The events list also no longer marks every row as someone else's until the viewer has loaded: rows show no share icon and only View Details until the session answers, and a failed `getCurrentUser` no longer leaves them that way.
- [2026-11-06] [Security] **Pressing a form before the page has finished loading no longer puts a password in the URL.** The sign-in, setup and sign-up forms had no `action`, so a press before React hydrated them was the browser's own GET, with the password, and on setup the installer's token, in the URL. That put them in the browser's history, in the `Referer` of what the page loaded next, and in a reverse proxy's access log. A slow connection or a password manager could do it. These forms now hold the press and act on it once the page is ready, so the person just gets signed in. So does forgot-password, which had the same problem with an email address. SMTP settings and adding a server had it with the SMTP password and an SSH key, and there the press now does nothing, because acting on it could save blanks over stored settings. Access logs from before this fix may hold such lines, so check with `grep -E '(password|confirmPassword|bootstrapToken|smtpPassword|sshKey)=' access.log`, remove any it finds, and change any password or key that appears.
- [2026-11-06] [Fix] Sign-in, setup, sign-up and forgot-password keep what was typed or filled in before the page finished loading. It was lost two ways. - [2026-11-06] [Fix] **A webhook event past 1 MB now reaches its receivers.** A delivery's request was limited by the constant meant for its response, so axios refused any body past 1 MB before sending it, and the queue repeated that until its retries ran out: no requests, and three failed rows. The inbound endpoint takes bodies up to 1 MB and escaping can make them up to 6 times as long, so a request of 300 KB could be answered with a success and its event never go out. A delivery now has its own limit of 8 MB, which holds anything the endpoint accepts. An event past that gets one failed row and no retries through the queue. `webhookSystem.test` and `webhookSystem.retryDelivery` refuse one with `PRECONDITION_FAILED`, and the endpoint answers 413 and stores nothing, which takes a webhook with `transformations` that copy fields. Deliveries that failed this way can now be sent with a manual retry, and every other failure is retried as before.
- [2026-11-06] [Fix] Restarting the orchestrator no longer abandons the jobs it was running. Any recreate, which meant any `.env` change and every upgrade, left the job's script running with nothing watching it: its result was lost, the sweeper failed or re-ran the job about 90 seconds later, and its sidecar and network stayed until removed by hand. Now a container job carries on through the restart. On SIGTERM the orchestrator exits at once and leaves running containers in place, and its next process finds them by label before it claims anything, renews their leases, follows them to the end and reports them, including a script that ended while no orchestrator was running. A job whose lease is gone has been failed or re-queued, so its containers are removed, killing the script if it's still going. The job's containers now stay until its result has been reported or spooled, so a process killed at any point leaves the next one something to work from. A job's next attempt also clears whatever its last one left, which previously failed it on a name conflict.
- [2026-11-06] [Fix] The orchestrator no longer waits 30 seconds for jobs it can leave running. A recreate stops the app first and starts nothing until the orchestrator has stopped, so that wait took the whole stack down for longer and used up the lease that lets the next process pick the job up. It now waits only for what can't be left, which is remote jobs and jobs still starting, then stops those and leaves them to the sweeper instead of reporting them cancelled. All compose files give it `stop_grace_period: 40s` for this. Completions spooled by the previous process are delivered on start instead of a minute later.
- [2026-11-06] [Fix] A worker that just started waits one lease length before its first sweep. A slow restart used to fail a healthy job just before its owner could renew it.
