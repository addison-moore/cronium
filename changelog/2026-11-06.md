# 2026-11-06

- [2026-11-06] [Fix] **A `bash` that a container job's script starts can now call the `cronium_*` helpers.** It inherited the functions but not the shell variables they read, so every call failed with `Error: Max retries exceeded` before making a request. They now read `CRONIUM_RUNTIME_API`, `CRONIUM_EXECUTION_TOKEN` and `CRONIUM_EXECUTION_ID` each time they run, and a script can use `MAX_RETRIES` and `RETRY_DELAY` itself, which used to break its helper calls. The bash runner image no longer sets `BASH_ENV`: it named a file the `/home` tmpfs hides, so it did nothing in a job. **Upgrade:** rebuild `cronium/runner:bash-alpine`. A script that unsets `CRONIUM_RUNTIME_API` or `CRONIUM_EXECUTION_ID` can no longer call helpers, and changing `CRONIUM_API` or `CRONIUM_EXEC_ID` no longer redirects them.
- [2026-11-06] [Security] **A sensitive system setting that can't be decrypted is no longer used as its own ciphertext.** After a change of `ENCRYPTION_KEY`, `getSmtpSettings`, `storage.getSetting` and `getAllSettings` logged the error and returned the stored value, so a password reset logged in to the SMTP server with ciphertext as the password, and an AI request could send it to the provider as a key. The single reads now throw `UnreadableSettingError` and nothing reaches the server. `admin.sendTestEmail`, `admin.resendInvitation` and a bulk resend say what's wrong and where to fix it, `admin.inviteUser` creates the user and warns that no invitation went (the users table used to show "Invitation email sent successfully" on every resend, before the server had answered, and no longer does), `ai.generateScript` answers `PRECONDITION_FAILED` with the reason, and listing models falls back with the reason. `userAuth.forgotPassword` is anonymous, so it answers as an unconfigured server does, for any email. `getAllSettings` now returns `{ settings, unreadable }`, so the admin settings page keeps loading: `getSystemSettings` adds `unreadableSecrets`, reports those keys as `has...: false`, and the email and AI forms ask for the value again. `getSmtpSettings` decrypts only the SMTP password now, so an AI key that can't be read no longer logs an error on every email, and an `OPENAI_API_KEY` in the environment still wins over a saved key nobody can read. A long plaintext made of base64 characters, saved before settings were encrypted, used to work only through this fallback: nothing tells it from ciphertext under a lost key, so it now has to be entered again too.
