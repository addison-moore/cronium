# 2026-11-06

- [2026-11-06] [Fix] **A `bash` that a container job's script starts can now call the `cronium_*` helpers.** It inherited the functions but not the shell variables they read, so every call failed with `Error: Max retries exceeded` before making a request. They now read `CRONIUM_RUNTIME_API`, `CRONIUM_EXECUTION_TOKEN` and `CRONIUM_EXECUTION_ID` each time they run, and a script can use `MAX_RETRIES` and `RETRY_DELAY` itself, which used to break its helper calls. The bash runner image no longer sets `BASH_ENV`: it named a file the `/home` tmpfs hides, so it did nothing in a job. **Upgrade:** rebuild `cronium/runner:bash-alpine`. A script that unsets `CRONIUM_RUNTIME_API` or `CRONIUM_EXECUTION_ID` can no longer call helpers, and changing `CRONIUM_API` or `CRONIUM_EXEC_ID` no longer redirects them.
- [2026-11-06] [Fix] **A bash container job now runs when the SDK can't work, instead of exiting 1 with no output.** `cronium.sh` ran `exit 1` as it loaded if the execution token or ID was empty, or if `curl` or `jq` wasn't on `PATH`. That ended the job's shell before its first line, and the job's loader hid the message, so an event env var setting `PATH` without `/usr/bin` was enough to cause it. The file now always loads, and each `cronium_*` helper checks when it's called: it prints the reason on stderr, makes no request and returns 1. The loader no longer hides stderr, so a bash job in an image without the SDK says so. The bash image's `healthcheck.sh` now passes with no token, as its comments said it should, and still fails with `curl` or `jq` missing. **Upgrade:** rebuild `cronium/runner:bash-alpine`. A job in that state that ignores a helper's status now ends with its script's own exit code, where it used to fail with 1. A process started with `env -u CRONIUM_EXECUTION_TOKEN` gets this error from any helper, where the runtime used to refuse it with a 401.
