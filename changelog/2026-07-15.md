# Changelog - 2026-07-15

- [2026-07-16] [Improvement] SQL Run Query now streams via a server-side cursor, so the row/byte limits bound the **fetch**, not just the payload. Previously `pg`/`mysql2` buffered the entire result set before any limit could be checked — `SELECT * FROM huge_table` could exhaust the app's heap (tool actions run in-process) before the cap ever fired; the cap only protected what was handed downstream. Run Query now pulls rows incrementally — a **`pg-cursor`** server-side cursor on Postgres (reading at most `maxRows + 1`, in 1,000-row batches) and mysql2's row **`.stream()`** on MySQL — and stops the moment either the row cap or the 5 MB byte budget is reached, so peak memory is bounded by the byte budget regardless of how large the result would have been. The driver interface is split accordingly: `query()` (streamed, bounded read) and `execute()` (buffered write — a write returns an affected-row count and has nothing to stream), replacing the old `run()` that sniffed the result shape. A shared `createRowAccumulator` enforces both limits identically across dialects and normalizes each row to JSON-safe values as it goes. Overflow is reported distinctly (`truncated` vs `bytesExceeded`) so the action fails with the right guidance. Verified against a live Postgres: a **5,000,000-row** query now stops at a 200 KB budget in under 10 seconds having read fewer than 1,000 rows (instead of buffering gigabytes), `EXPLAIN` streams through the cursor fine, and an empty result still reports its columns. Tests: 8 live-DB integration cases + rewritten driver tests (fake cursor/stream, asserting the cursor is never asked for more than `maxRows + 1`) + accumulator unit tests. Verified: typecheck + lint clean, 141 passing (+8 integration skipped), production build compiles all 49 routes.

- [2026-07-16] [Bug Fix] Unified I/O output is size-capped for tool actions, and SQL Run Query fails instead of silently truncating. Prompted by the ETL case (a user needing >10k rows): the 10k row cap **silently** returned a shortened result with `truncated: true`, so a job could report success while dropping rows — data loss an ETL couldn't detect. Run Query now **fails** when the cap is exceeded, with an actionable message (add a `LIMIT`, raise Max Rows, or move bulk work to a server-side `INSERT ... SELECT` / a streaming Script event), and **Max Rows** is back as an _optional_ field (blank = 10,000, ceiling 1,000,000) so moderate extracts work. Also closed a real asymmetry: a script's `cronium.output()` was capped at 5 MB by the `/executions/[id]/output` route, but **tool-action output had no cap at all** — so a tool could publish a payload a script would have been refused, straight into `job.result` (jsonb). Both now share `MAX_UNIFIED_IO_OUTPUT_BYTES` (`lib/unified-io/limits.ts`, 5 MB), enforced for every output-producing tool action in `runInProcessJob`; exceeding it fails the job rather than dropping the payload (the same silent-loss trap). Note the cap bounds the _payload_, not the driver's fetch — the driver still buffers the full result before the check, so truly large extracts belong on the zero-transfer paths, now documented in `docs/tools/SQL_TOOL.md` ("Large result sets and bulk ETL", with `INSERT ... SELECT` and server-side-cursor script examples). Tests: fail-on-cap, maxRows override, and the oversize-output job failure. Verified: typecheck + lint clean, 135 passing (+5 integration skipped), live-Postgres integration re-verified, production build compiles.

- [2026-07-15] [Improvement] SQL tool action form UX + the event Timeout now applies to tool actions. Four changes from testing the SQL event form: (1) **Query/Statement fields now render in a SQL code editor** (Monaco `sql` language) instead of a plain text input — `ActionParameterForm` recognizes a SQL field (name `query`/`statement` or a description containing "SQL") and switches to Monaco, matching the script-event editors. (2) **The event's Timeout setting now bounds in-process tool actions.** It previously did nothing for tool/HTTP actions (only container/SSH jobs read it). `executeToolAction` now resolves `event.timeoutValue`/`timeoutUnit` to ms (new `lib/scheduler/event-timeout.ts`), passes it on the execution context, and enforces it as an overall cap around `action.execute` (new `lib/scheduler/with-timeout.ts`); the SQL driver uses the same value as its statement timeout so a slow query is cancelled DB-side within the budget. (3) **Removed the redundant per-action `Timeout Ms` field** from both SQL actions — the event Timeout is the single source. (4) **Removed the `Max Rows` field**; results are capped at an internal 10,000-row backstop (`truncated` flag retained) and users control size with `LIMIT`. Also clarified the optional **Parameters** field with inline help (it's the injection-safe bind map for `:name` placeholders) and made the generic complex-field renderer show a field's description. Existing SQL configs keep working (removed keys are ignored by the schema). Docs updated. Verified: typecheck + lint clean, 132 tests passing (+5 integration skipped; live Postgres integration re-verified), production build generates all routes.

- [2026-07-15] [Feature] Finished the SQL Database tool (non-Snowflake): user docs, a live-database integration test, and a worked write example. Added `docs/tools/SQL_TOOL.md` (connecting, both actions, safe parameter binding, the Unified I/O hand-off, and security/least-privilege guidance). Added `postgres-integration.test.ts` — an integration suite that runs the **real** `pg` adapter (unmocked) against a Postgres pointed to by `CRONIUM_SQL_TEST_PG_URL`, using only read-only built-ins (`generate_series`, casts, `now()`) so no tables are created and nothing is written; it verifies named-placeholder binding, `BIGINT`→string precision, timestamp/date→ISO coercion, the row cap/`truncated` flag, the end-to-end run-query action, and the read-only guard. The suite auto-skips when the env var is unset, so `pnpm test` stays green without a database; verified passing against the dev Postgres. Added an `execute-statement` example. Suite: 128 passing + 5 integration skipped (133 total).

- [2026-07-15] [Feature] SQL Database tool (PostgreSQL + MySQL) with Unified I/O integration. A new `sql` tool (`src/tools/plugins/sql/`) lets events and workflows query SQL databases, following the single-tool-with-per-dialect-adapters design in `_plans/sql-tool/PLAN.md`. One tool, one UI, one action set; `execute()` dispatches to a driver adapter chosen by `credentials.dialect`. **Actions:** `run-query` (read-only SELECT/WITH; `producesOutput: true` so its `{ columns, rows, rowCount, truncated }` flows to the next workflow step via `cronium.input()`) and `execute-statement` (INSERT/UPDATE/DELETE/DDL → affected row count; single attempt). **Adapters** (`drivers/`, dialect-agnostic `SqlDriver` interface): Postgres (`pg`, already a dep) and MySQL (`mysql2`, added), each dynamically `import()`-ed server-side only and opening a short-lived connection per call. **Safety:** named `:placeholders` are rewritten to `$n`/`?` and bound by the driver (never string-concatenated), a comment/string-aware scanner keeps `:name` out of literals and `::` casts, a read-only guard blocks mutations and stacked statements on Run Query, a row cap sets `truncated`, and a per-statement timeout applies. Driver values are coerced JSON-safe (Date→ISO, bigint/decimal→string, Buffer→base64) so results survive Unified I/O. Credentials (`host`/`port`/`database`/`user`/`password`/`ssl`) are encrypted at rest; `password` is auto-redacted/merged by the secret-key pattern. `:named` values in the Parameters map are rendered from `{{cronium.input.*}}`/`{{cronium.getVariables.*}}` by the existing template processor, then bound — the requested "use variables/inputs in queries" done the injection-safe way. Registered via one manifest line (`tool-registry.ts`) + one client-plugin line (`tools/plugins/index.ts`); `mysql2` externalized in `next.config.mjs` (it uses `node:`-scheme builtins the client webpack can't resolve and is server-only). Snowflake is deferred to a later increment (the adapter interface already fits it). Tests: 32 new (placeholder rewriting incl. casts/strings/comments, JSON-safe coercion, read-only/single-statement guards, param coercion, and Postgres/MySQL adapter normalization with mocked drivers). Verified: typecheck + lint clean, 127 app tests passing, production build compiles and generates all routes.
