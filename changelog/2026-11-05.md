# 2026-11-05

- [2026-11-05] [Fix] A workflow run that times out now writes its timeout line on its own workflow, under its owner. The sweep used the run's id as the workflow id, so run 2 of one user's workflow wrote `Workflow execution timed out` onto workflow 2, which could belong to another user, and the run's own workflow showed nothing. Where no workflow had that id, the insert failed its foreign key and the run's running jobs were never timed out here, which left them to the lease sweeper. A failed log write no longer affects the jobs, and finding them no longer loads the whole `jobs` table for each stuck run.
- [2026-11-05] [Fix] `POST /api/admin/cleanup` with `type: "workflow"` takes a run id, and its response now says so. It leaves a finished run alone, where it used to overwrite the result with `TIMEOUT` and add a timeout line, and it answers 404 when no run with that id is running, where it used to report success regardless. A failed update returns 500.
- [2026-11-05] [Fix] `POST /api/admin/cleanup` answers 400 to a request it can't read. A missing or zero `id`, an unknown `type`, an `id` with no `type`, or a body that isn't a JSON object used to fall through to the full sweep, which also times out every job older than 15 minutes, and `"id": true` timed out run 1. `{}` and `{"type":"all"}` still run the sweep. A cleanup that fails is now audited as `error`, where it left no audit line.
- [2026-11-05] [Fix] A timed-out workflow run records how long it really ran, in `total_duration` and its timeout line, and sets `updated_at`. It used to report the 30-minute limit, including for a run an admin stopped after two minutes or one stuck for hours. `total_duration` is capped at what its integer column holds, about 24.8 days, so a longer stuck run can still time out.
- [2026-11-05] [Fix] Migration `0014` moves timeout lines already on the wrong workflow to the run's own workflow and owner, on databases from the old `drizzle-kit push` flow as well. A line moves only when it can be tied to its run: no owner, the status, level and message only the old code wrote, and a timestamp equal to that run's `completed_at`. Two kinds stay where they are: a line whose run has since been deleted, and the first line of a run timed out twice through the admin route.
- [2026-11-05] [Test] A test now fails on a migration journal that is out of order. Drizzle skips an entry older than the last one a database applied, with no error, and two branches adding a migration at once can produce that.
- [2026-11-05] [Fix] A workflow run that times out can no longer have its jobs start afterwards. Its queued jobs, including ones waiting out a retry backoff, now time out with it. They used to stay queued and run whenever an orchestrator or the worker next claimed them, long after the run was reported as timed out. This also frees their overlap slot and finishes their log rows, which stayed `PENDING`. A job waiting to retry says so in its error, instead of claiming it never started. A job created while the run was timing out is caught too. The worker also no longer runs a tool action or HTTP request whose job ended between its claim and its start, which covers a job cancelled in that gap as well.
- [2026-11-05] [Fix] The steps of a timed-out run now finish, along with their telemetry. They stayed `DISPATCHED` or `PENDING` with telemetry `RUNNING`, so a run's history showed **Timeout** over a step marked **Running**, and its `successfulEvents` and `failedEvents` stayed 0. A step whose job finished before the timeout takes that job's result, one whose job was cut off is `FAILED`, and one that never started is `SKIPPED`. The worker's cleanup pass retries anything still open under a timed-out run, so runs from before this change settle too, up to 100 per pass, with their steps closed at the time the run timed out. A pass keeps its place across runs, so ones that can't settle don't hold up the rest. It also gives up after 5 seconds on a run another process has locked, including a stuck run it is timing out, and tries again on a later pass, so one hung transaction can't stall the cleanup.
- [2026-11-05] [Fix] The workflow graph no longer stays on **Executing** after the run it is following times out. Two of its three checks for a finished run left out `TIMEOUT`.
- [2026-11-05] [Fix] A job timed out by the cleanup service reports how long it actually ran in its log, and no duration if it never started, instead of a fixed 15 minutes. Execution rows from earlier attempts keep the results they reported.
- [2026-11-05] [Fix] A code editor that can't download Monaco no longer takes the page down. It used to throw to the route's error page, which lost unsaved form input and could only be cleared by a full reload. The form now stays up with the script in a plain text box, edits still reach the form, and the real editor takes over when a retry succeeds.
- [2026-11-05] [Fix] Bash scripts get syntax highlighting. `MonacoEditor` passed `bash` as the language, and Monaco's ID is `shell`, so they showed as plain text.
- [2026-11-05] [Fix] The code editor's expand and minimize buttons no longer submit the form around them. They had no `type`, so in the event form, clicking expand saved the event and left the page.
- [2026-11-05] [Security] An editor mounted without the app's Monaco setup now fails on our own origin instead of running Monaco from jsDelivr, and `worker-src` no longer allows `blob:`, which nothing has used since Monaco's workers became bundled chunks.
- [2026-11-05] [Chore] Stopped building a CSS language worker that no editor can ask for.
- [2026-11-05] [Test] The guard on direct `@monaco-editor/react` use now catches dynamic imports, `require` and re-exports as well as static imports, and the E2E suite fails if Monaco reaches the `commons` chunk or the server bundle.
- [2026-11-05] [Docs] `docs/DEPLOYMENT.md` now says building from source needs about 8GB. Its 4GB minimum applies to running the published images, and `next build` alone peaks above that.
- [2026-11-05] [Security] **One rejected entry can no longer stop the tool audit log.** `AuditLogger.flush` wrote each batch in one insert and put the whole batch back on any failure, so a single entry the database rejected failed every flush after it: nothing more reached `tool_audit_logs` until a restart, which also lost the buffer, and the buffer grew without limit until then. Any failed tool action whose config named no tool did this, because the executor passed `toolId: 0`. So did an event still pointing at a deleted credential, a credential deleted in the seconds before a flush, a NUL byte in an error message, and an `actionId` nested too deeply for `JSON.stringify`. A missing tool id is now stored as null. Entries are cleaned when they are logged, so one bad value costs only itself: NUL bytes are stripped, long values are cut to fit, nesting stops at 16 levels, and each entry has a size limit. A rejected batch is retried one entry at a time, and each entry gives up only what is still rejected: a tool id that can't be referenced moves into `action_details`, and contents that still can't be stored leave a row saying who did what and whether it worked, with `action_details.detailsRejected` and the full entry in the server log, secrets masked. An entry is dropped, and logged the same way, only when the database rejects even that row for something its values can cause. Anything that isn't the entry's fault, such as a refused connection, a missing table or a sequence left behind by a restore, keeps entries for retry, up to 1,000 entries and about 32MB: past that the oldest go to the server log. `log()` no longer waits for a flush, so an audit call can't slow down the action it records. Flush failures also stop logging Drizzle's message, which repeated every value in the batch, and what they quote from a rejected value is masked and cut short. `tests/storage/audit-log-flush.test.ts` covers this against real Postgres.
- [2026-11-05] [Security] **Databases from the old `drizzle-kit push` flow lose their stored webhook header values on the next boot.** Migration `0012` had no `-- cronium:custom-migration` marker, so on those databases it was stamped as applied without running, and `webhook_deliveries.headers` kept custom header values in plaintext, including credentials like `Authorization`, where the delivery-history API returns them. Migration `0015` repeats the scrub with the marker, and reaches a database already stamped past `0012` as well. On a row from before the fix it removes each custom header and `X-Webhook-Signature`, leaving what `0012` leaves, and it empties a value that isn't an object. It also deletes the `logRetentionDays` setting, which `0013` skipped the same way. It isn't a copy of `0012`, whose statement would also remove the custom header names that deliveries written since keep as `[redacted]`. Where `0012` and `0013` already ran, it rewrites no row. A test now fails on a migration holding something push can't apply without the marker, and on a marked one holding something push has already applied. The values stay in old row versions until the next vacuum, and in backups, so anyone on that flow should rotate those credentials.
