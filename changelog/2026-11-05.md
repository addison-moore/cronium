# 2026-11-05

- [2026-11-05] [Fix] A workflow run that times out now writes its timeout line on its own workflow, under its owner. The sweep used the run's id as the workflow id, so run 2 of one user's workflow wrote `Workflow execution timed out` onto workflow 2, which could belong to another user, and the run's own workflow showed nothing. Where no workflow had that id, the insert failed its foreign key and the run's running jobs were never timed out here, which left them to the lease sweeper. A failed log write no longer affects the jobs, and finding them no longer loads the whole `jobs` table for each stuck run.
- [2026-11-05] [Fix] `POST /api/admin/cleanup` with `type: "workflow"` takes a run id, and its response now says so. It leaves a finished run alone, where it used to overwrite the result with `TIMEOUT` and add a timeout line, and it answers 404 when no run with that id is running, where it used to report success regardless. A failed update returns 500.
- [2026-11-05] [Fix] `POST /api/admin/cleanup` answers 400 to a request it can't read. A missing or zero `id`, an unknown `type`, an `id` with no `type`, or a body that isn't a JSON object used to fall through to the full sweep, which also times out every job older than 15 minutes, and `"id": true` timed out run 1. `{}` and `{"type":"all"}` still run the sweep. A cleanup that fails is now audited as `error`, where it left no audit line.
- [2026-11-05] [Fix] **Saving an event is all or nothing.** `events.update` and `PATCH /api/events/{id}` saved an event's fields, then deleted its variables and added them back one row at a time, then changed its server links, with no transaction around them. So a dropped connection, a statement timeout or a vault error partway answered 500, lost every variable not yet added, and could leave a new script with its old variables. A job dispatched during a save could also get part of the set, and two saves at once could mix, leaving duplicate keys. The fields, variables and server links now save in one transaction, with values encrypted before it opens and the schedule updated after it commits, and saves to the same event take turns. **A failed create leaves nothing behind.** `events.create`, `POST /api/events` and fork now write the event, its variables and its server links in one transaction. The event used to stay after the 500, and an `ACTIVE` scheduled one started running about a minute later with whichever variables had made it. `PATCH /api/events/{id}` can also now change only the variables or servers: with no other field it answered 500 with `No values to set`, and wrote nothing.
- [2026-11-05] [Fix] A timed-out workflow run records how long it really ran, in `total_duration` and its timeout line, and sets `updated_at`. It used to report the 30-minute limit, including for a run an admin stopped after two minutes or one stuck for hours. `total_duration` is capped at what its integer column holds, about 24.8 days, so a longer stuck run can still time out.
- [2026-11-05] [Fix] Migration `0014` moves timeout lines already on the wrong workflow to the run's own workflow and owner, on databases from the old `drizzle-kit push` flow as well. A line moves only when it can be tied to its run: no owner, the status, level and message only the old code wrote, and a timestamp equal to that run's `completed_at`. Two kinds stay where they are: a line whose run has since been deleted, and the first line of a run timed out twice through the admin route.
- [2026-11-05] [Test] A test now fails on a migration journal that is out of order. Drizzle skips an entry older than the last one a database applied, with no error, and two branches adding a migration at once can produce that.
- [2026-11-05] [Fix] **An event's environment variable can hold a long value.** `env_vars.value` was `varchar(255)` and holds an encrypted envelope of about 60 characters plus 4/3 of the value, so anything over 150 characters, which covers ordinary JWTs and long API keys, failed to save with `Failed to update event`. A save deletes the event's variables and adds them back one at a time, so the failure also lost every variable after the long one. Migration `0016` makes the column `text` without rewriting the table, and on a database from the old `drizzle-kit push` flow, push makes the same change and keeps the rows. A value can now be up to 128 KB, and an event's variables up to 1 MB in total, because Linux won't start a process with more: the job would fail as it starts with `argument list too long`. The form, REST, tRPC, MCP and JSON import refuse anything past that before writing, and say why. They do the same for more than 1,000 variables, a key over 255 characters and a NUL in a key or value, and a NUL in a key could still empty an event. The form shows these beside the row and scrolls to them, because its submit button is a screen below. It also says when a value loses its line breaks, which its single-line field turns into spaces on paste and which stops a PEM key working. Values set through the API keep theirs. `POST` and `PATCH /api/events` answer 400 instead of 500 to a body that isn't JSON, including one cut off at the proxy's 10 MB. A list of jobs, which is what the Jobs page shows, no longer returns the job's copy of those variables: at the new limit 50 jobs made that page 67 MB, and sent all of it to the browser. It's now 230 KB, and `jobs.get` still returns them.
- [2026-11-05] [Fix] A workflow run that times out can no longer have its jobs start afterwards. Its queued jobs, including ones waiting out a retry backoff, now time out with it. They used to stay queued and run whenever an orchestrator or the worker next claimed them, long after the run was reported as timed out. This also frees their overlap slot and finishes their log rows, which stayed `PENDING`. A job waiting to retry says so in its error, instead of claiming it never started. A job created while the run was timing out is caught too. The worker also no longer runs a tool action or HTTP request whose job ended between its claim and its start, which covers a job cancelled in that gap as well.
- [2026-11-05] [Fix] The steps of a timed-out run now finish, along with their telemetry. They stayed `DISPATCHED` or `PENDING` with telemetry `RUNNING`, so a run's history showed **Timeout** over a step marked **Running**, and its `successfulEvents` and `failedEvents` stayed 0. A step whose job finished before the timeout takes that job's result, one whose job was cut off is `FAILED`, and one that never started is `SKIPPED`. The worker's cleanup pass retries anything still open under a timed-out run, so runs from before this change settle too, up to 100 per pass, with their steps closed at the time the run timed out. A pass keeps its place across runs, so ones that can't settle don't hold up the rest. It also gives up after 5 seconds on a run another process has locked, including a stuck run it is timing out, and tries again on a later pass, so one hung transaction can't stall the cleanup.
