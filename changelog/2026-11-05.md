# 2026-11-05

- [2026-11-05] [Fix] A workflow run that times out now writes its timeout line on its own workflow, under its owner. The sweep used the run's id as the workflow id, so run 2 of one user's workflow wrote `Workflow execution timed out` onto workflow 2, which could belong to another user, and the run's own workflow showed nothing. Where no workflow had that id, the insert failed its foreign key and the run's running jobs were never timed out here, which left them to the lease sweeper. A failed log write no longer affects the jobs, and finding them no longer loads the whole `jobs` table for each stuck run.
- [2026-11-05] [Fix] `POST /api/admin/cleanup` with `type: "workflow"` takes a run id, and its response now says so. It leaves a finished run alone, where it used to overwrite the result with `TIMEOUT` and add a timeout line, and it answers 404 when no run with that id is running, where it used to report success regardless. A failed update returns 500.
- [2026-11-05] [Fix] Migration `0013` moves timeout lines already on the wrong workflow to the run's own workflow and owner, on databases from the old `drizzle-kit push` flow as well. A line moves only when it can be tied to its run: no owner, the status, level and message only the old code wrote, and a timestamp equal to that run's `completed_at`. Two kinds stay where they are: a line whose run has since been deleted, and the first line of a run timed out twice through the admin route.
- [2026-11-05] [Test] A test now fails on a migration journal that is out of order. Drizzle skips an entry older than the last one a database applied, with no error, and two branches adding a migration at once can produce that.
- [2026-11-05] [Fix] A workflow run that times out can no longer have its jobs start afterwards. Its queued jobs, including ones waiting out a retry backoff, now time out with it. They used to stay queued and run whenever an orchestrator or the worker next claimed them, long after the run was reported as timed out. This also frees their overlap slot and finishes their log rows, which stayed `PENDING`. A job created while the run was timing out is caught too. The worker also no longer runs a tool action or HTTP request whose job ended between its claim and its start, which covers a job cancelled in that gap as well.
- [2026-11-05] [Fix] The steps of a timed-out run now finish, along with their telemetry. They stayed `DISPATCHED` or `PENDING` with telemetry `RUNNING`, so a run's history showed **Timeout** over a step marked **Running**, and its `successfulEvents` and `failedEvents` stayed 0. A step whose job finished before the timeout takes that job's result, one whose job was cut off is `FAILED`, and one that never started is `SKIPPED`. The worker's cleanup pass retries anything still open under a timed-out run, so runs from before this change settle too, up to 100 per pass, with their steps closed at the time the run timed out.
- [2026-11-05] [Fix] The workflow graph no longer stays on **Executing** after the run it is following times out. Two of its three checks for a finished run left out `TIMEOUT`.
- [2026-11-05] [Fix] A job timed out by the cleanup service reports how long it actually ran in its log, and no duration if it never started, instead of a fixed 15 minutes. Execution rows from earlier attempts keep the results they reported.
