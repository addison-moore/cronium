# 2026-11-05

- [2026-11-05] [Fix] A workflow run that times out now writes its timeout line on its own workflow, under its owner. The sweep used the run's id as the workflow id, so run 2 of one user's workflow wrote `Workflow execution timed out` onto workflow 2, which could belong to another user, and the run's own workflow showed nothing. Where no workflow had that id, the insert failed its foreign key and the run's running jobs were never timed out here, which left them to the lease sweeper. A failed log write no longer affects the jobs, and finding them no longer loads the whole `jobs` table for each stuck run.
- [2026-11-05] [Fix] `POST /api/admin/cleanup` with `type: "workflow"` takes a run id, and its response now says so. It leaves a finished run alone, where it used to overwrite the result with `TIMEOUT` and add a timeout line, and it answers 404 when no run with that id is running, where it used to report success regardless. A failed update returns 500.
- [2026-11-05] [Fix] `POST /api/admin/cleanup` answers 400 to a request it can't read. A missing or zero `id`, an unknown `type`, an `id` with no `type`, or a body that isn't a JSON object used to fall through to the full sweep, which also times out every job older than 15 minutes, and `"id": true` timed out run 1. `{}` and `{"type":"all"}` still run the sweep. A cleanup that fails is now audited as `error`, where it left no audit line.
- [2026-11-05] [Fix] A timed-out workflow run records how long it really ran, in `total_duration` and its timeout line, and sets `updated_at`. It used to report the 30-minute limit, including for a run an admin stopped after two minutes or one stuck for hours. `total_duration` is capped at what its integer column holds, about 24.8 days, so a longer stuck run can still time out.
- [2026-11-05] [Fix] Migration `0014` moves timeout lines already on the wrong workflow to the run's own workflow and owner, on databases from the old `drizzle-kit push` flow as well. A line moves only when it can be tied to its run: no owner, the status, level and message only the old code wrote, and a timestamp equal to that run's `completed_at`. Two kinds stay where they are: a line whose run has since been deleted, and the first line of a run timed out twice through the admin route.
- [2026-11-05] [Test] A test now fails on a migration journal that is out of order. Drizzle skips an entry older than the last one a database applied, with no error, and two branches adding a migration at once can produce that.
- [2026-11-05] [Fix] A workflow run that times out can no longer have its jobs start afterwards. Its queued jobs, including ones waiting out a retry backoff, now time out with it. They used to stay queued and run whenever an orchestrator or the worker next claimed them, long after the run was reported as timed out. This also frees their overlap slot and finishes their log rows, which stayed `PENDING`. A job waiting to retry says so in its error, instead of claiming it never started. A job created while the run was timing out is caught too. The worker also no longer runs a tool action or HTTP request whose job ended between its claim and its start, which covers a job cancelled in that gap as well.
- [2026-11-05] [Fix] The steps of a timed-out run now finish, along with their telemetry. They stayed `DISPATCHED` or `PENDING` with telemetry `RUNNING`, so a run's history showed **Timeout** over a step marked **Running**, and its `successfulEvents` and `failedEvents` stayed 0. A step whose job finished before the timeout takes that job's result, one whose job was cut off is `FAILED`, and one that never started is `SKIPPED`. The worker's cleanup pass retries anything still open under a timed-out run, so runs from before this change settle too, up to 100 per pass, with their steps closed at the time the run timed out. A pass keeps its place across runs, so ones that can't settle don't hold up the rest. It also gives up after 5 seconds on a run another process has locked, including a stuck run it is timing out, and tries again on a later pass, so one hung transaction can't stall the cleanup.
- [2026-11-05] [Fix] The workflow graph no longer stays on **Executing** after the run it is following times out. Two of its three checks for a finished run left out `TIMEOUT`.
- [2026-11-05] [Fix] A job timed out by the cleanup service reports how long it actually ran in its log, and no duration if it never started, instead of a fixed 15 minutes. Execution rows from earlier attempts keep the results they reported.
- [2026-11-05] [Fix] A code editor that can't download Monaco no longer takes the page down. It used to throw to the route's error page, which lost unsaved form input and could only be cleared by a full reload. The form now stays up with the script in a plain text box, edits still reach the form, and the real editor takes over when a retry succeeds.
- [2026-11-05] [Fix] Bash scripts get syntax highlighting. `MonacoEditor` passed `bash` as the language, and Monaco's ID is `shell`, so they showed as plain text.
- [2026-11-05] [Fix] The code editor's expand and minimize buttons no longer submit the form around them. They had no `type`, so in the event form, clicking expand saved the event and left the page.
- [2026-11-05] [Security] An editor mounted without the app's Monaco setup now fails on our own origin instead of running Monaco from jsDelivr, and `worker-src` no longer allows `blob:`, which nothing has used since Monaco's workers became bundled chunks.
- [2026-11-05] [Chore] Stopped building a CSS language worker that no editor can ask for.
- [2026-11-05] [Test] The guard on direct `@monaco-editor/react` use now catches dynamic imports, `require` and re-exports as well as static imports, and the E2E suite fails if Monaco reaches the `commons` chunk or the server bundle.
- [2026-11-05] [Docs] `docs/DEPLOYMENT.md` now says building from source needs about 8GB. Its 4GB minimum applies to running the published images, and `next build` alone peaks above that.
- [2026-11-05] [Security] **One rejected entry can no longer stop the tool audit log.** `AuditLogger.flush` wrote each batch in one insert and put the whole batch back on any failure, so a single entry the database rejected failed every flush after it: nothing more reached `tool_audit_logs` until a restart, which also lost the buffer, and the buffer grew without limit until then. Any failed tool action whose config named no tool did this, because the executor passed `toolId: 0`. So did an event still pointing at a deleted credential, a credential deleted in the seconds before a flush, a NUL byte in an error message, and an `actionId` nested too deeply for `JSON.stringify`. A missing tool id is now stored as null. Entries are cleaned when they are logged, so one bad value costs only itself: NUL bytes are stripped, long values are cut to fit, nesting stops at 16 levels, and each entry has a size limit. A rejected batch is retried one entry at a time, and each entry gives up only what is still rejected: a tool id that can't be referenced moves into `action_details`, and contents that still can't be stored leave a row saying who did what and whether it worked, with `action_details.detailsRejected` and the full entry in the server log, secrets masked. An entry is dropped, and logged the same way, only when the database rejects even that row for something its values can cause. Anything that isn't the entry's fault, such as a refused connection, a missing table or a sequence left behind by a restore, keeps entries for retry, up to 1,000 entries and about 32MB: past that the oldest go to the server log. `log()` no longer waits for a flush, so an audit call can't slow down the action it records. Flush failures also stop logging Drizzle's message, which repeated every value in the batch, and what they quote from a rejected value is masked and cut short. `tests/storage/audit-log-flush.test.ts` covers this against real Postgres.
- [2026-11-05] [Security] **Webhook secrets, webhook headers and user variables saved before encryption at rest (July 2026) can now be encrypted.** They stayed plaintext until that exact field was next written, so an edit to a webhook's URL left its secret and headers readable in every copy of the database. `rotate:secrets --encrypt-legacy` encrypts them under the same record bindings the app writes, with no change for senders, subscribers or scripts. It is run by an operator, not at boot: see `docs/ENVIRONMENT_VARIABLES.md`. It can be repeated and interrupted, doesn't overwrite a value changed while it runs, leaves a failed row exactly as it was and names it, ends by saying how many legacy rows remain, and stops before writing if the database holds encrypted values the key can't read. That check covers vault values, tool credentials, OAuth tokens and older ciphertext in server credentials, env vars, MFA secrets, sensitive settings and unhashed API tokens, so a database old enough to hold no vault values is checked too. A value a read merely passes through doesn't count in the key's favour, and with nothing encrypted anywhere there's nothing to check against. The published image now ships the tool as `dist/rotate-secrets.cjs`, since it had no way to run it before, and the worker logs a warning at boot while such rows exist, from a count that decrypts nothing and needs no key. The self-hosting guide on the docs site has the commands. The old values stay in the table files until `VACUUM FULL`, and in WAL and existing backups until those are gone. `tests/storage/legacy-secrets.test.ts` covers this against real Postgres.
- [2026-11-05] [Fix] **The key rotation runbook gave the running services the new key too late.** It restarted them only at the end, so a service still on the old key couldn't read any row the driver had moved. On a running app with a throwaway database, signed webhooks got a 500, the variables page and `cronium.getVariable()` failed, tool credentials and env vars came back empty, MFA sign-ins were refused as a wrong code, and saving an event stored its env vars blank. A value the app saved after the driver's last pass stayed under the old key, and after the final restart neither it nor anything else on its owner's variables page could be read. The new order restarts the app and worker with both keys first: about 500 reads all succeeded while the driver moved 20,000 rows. `docs/ENVIRONMENT_VARIABLES.md` no longer says there is no downtime, and lists what remains: two restarts of a few seconds each, jobs running at the first one, jobs still queued when the old key goes, and the settings and API tokens the driver doesn't count.
- [2026-11-05] [Fix] `infra/docker/docker-compose.yml` and both dev compose files pass `ENCRYPTION_KEYS_RETIRED` to the app and worker. They list each variable by name and this one was missing, so a retired key never reached those containers, and restarting with a new key would have left every stored secret unreadable. `docker-compose.example.yml` passes it through `env_file` and needed no change.
- [2026-11-05] [Docs] `docs/DEPLOYMENT.md` no longer says rotating `ENCRYPTION_KEY` means restarting and re-entering tool credentials. Changing it in `.env` alone makes every stored secret unreadable, so it now links to the runbook.
- [2026-11-05] [Fix] `rotate:secrets` counts plaintext webhook headers as `legacy`, where it skipped them without counting, and no longer warns that plaintext webhook and variable values would be orphaned by a key change or that they encrypt themselves on the next save. A mistyped flag now stops the run: `--dry-rn` used to run for real.
- [2026-11-05] [Security] **Databases from the old `drizzle-kit push` flow lose their stored webhook header values on the next boot.** Migration `0012` had no `-- cronium:custom-migration` marker, so on those databases it was stamped as applied without running, and `webhook_deliveries.headers` kept custom header values in plaintext, including credentials like `Authorization`, where the delivery-history API returns them. Migration `0015` repeats the scrub with the marker, and reaches a database already stamped past `0012` as well. On a row from before the fix it removes each custom header and `X-Webhook-Signature`, leaving what `0012` leaves, and it empties a value that isn't an object. It also deletes the `logRetentionDays` setting, which `0013` skipped the same way. It isn't a copy of `0012`, whose statement would also remove the custom header names that deliveries written since keep as `[redacted]`. Where `0012` and `0013` already ran, it rewrites no row. A test now fails on a migration holding something push can't apply without the marker, and on a marked one holding something push has already applied. The values stay in old row versions until the next vacuum, and in backups, so anyone on that flow should rotate those credentials.
- [2026-11-05] [Security] **The tool audit log no longer loses its last entries when a process stops.** Entries wait in memory for up to five seconds, and nothing wrote them out on a graceful stop, because `auditLogger.shutdown()` had no callers. A credential created, changed or deleted in the seconds before a restart left no row, and neither did a tool action the worker had just finished or waited for while draining. Stopping a real worker wrote 0 of 5 rows, and stopping a real Next server wrote 0 of 3. The worker now writes them after draining its jobs, and the Next server after finishing its requests. That needed three changes of its own: Next exits within milliseconds of SIGTERM with no hook to run first, so once a signal arrives `process.exit` waits for the logger; `instrumentation.ts` moved to `src/`, because Next never loaded it from the app root; and the logger is now one per process, because Next builds the module once per layer and the routes were logging to a different copy. If the logger can't load, as on a value only `env.mjs` rejects, the Next server logs that and otherwise runs as it did, because Next answers every route with a 500 once `register()` throws. The socket server never loads the logger, so it has nothing to write, and a test fails if that changes.
- [2026-11-05] [Security] **`AuditLogger.shutdown()` gives up after 5 seconds, and what it couldn't write goes to the server log.** It used to wait with no limit for a full batch's flush, and not at all for one the interval started, whose entries could then be lost. It now waits for any write under way, retries through a short outage, and once time is up logs each remaining entry as `[AuditLog] DROPPED`, secrets masked, then waits for the log to take them, because `process.exit` discards what hasn't reached a pipe. An entry whose write was still under way says it may also have been written. An entry logged once `shutdown()` has finished with the buffer goes straight to the server log the same way, so one that arrives during that wait or after it returns still leaves a line.
- [2026-11-05] [Fix] A hung database no longer stops the worker from exiting. It waited with no limit for Postgres to close its `LISTEN` connection, so it never got as far as draining, and only Docker's kill ended it. On a paused Postgres, a real worker now exits in about 8 seconds at most when no job is running, about 35 when a job is stuck on the database and takes its whole drain, and the Next server in about 15, where it now stops waiting for requests after 10 seconds. The worker's drain also waits for a claim already under way, up to 3 seconds, so a job claimed as the worker stopped isn't cut off. A claim that takes longer doesn't start its jobs when it does finish, because the exit would cut them off partway and the sweeper would then run them again. They stay claimed, and when the lease runs out the sweeper requeues or fails them under their lease-loss policy.
- [2026-11-05] [Fix] **`tool_audit_logs.created_at` is now when the event happened**, not when a flush wrote the row. An entry held through an outage got the time the outage ended, every row in a batch got the same time, and all of them were off by the database session's UTC offset when read back if that session wasn't in UTC. The time is taken when the entry is logged, on the app's clock, and is also in what goes to the server log. **Upgrade:** on a database whose sessions aren't in UTC, older rows still hold local time, so new rows jump by the offset at the upgrade. Rows from the retention purge still use the database's clock.
- [2026-11-05] [Infrastructure] Both compose files now give `cronium-app` 20 seconds and `cronium-worker` 40 seconds to stop, in place of Docker's default 10, so the worker's 30-second drain and the audit log's last write can finish before Docker kills them. `docker-compose.dev.local-app.yml` gives its worker the same 40. If you run the images another way, give them the same. A stop with nothing running still takes under 2 seconds.
- [2026-11-05] [Fix] **A script running when `ENCRYPTION_KEY` changes now finishes normally.** Job tokens were checked against the active key only, so from the first restart of a key rotation every call a running script made got a 403. The orchestrator dropped its completion report, and the sweeper then failed the job or ran it again from the start, even if the script had finished. The app now also accepts a token signed under a key in `ENCRYPTION_KEYS_RETIRED`, and new tokens are signed with the active key only. A key taken out of the list is refused. A malformed list is ignored with a warning, and tokens under the active key keep working. On a real app, a token claimed under the old key got a 403 on `/api/internal/variables/<userId>/<key>` and `/api/internal/jobs/<id>/status` after the restart, and now gets a 200.
- [2026-11-05] [Security] **`docs/ENVIRONMENT_VARIABLES.md` has a separate key rotation path for a key that leaked.** Anyone holding a key in `ENCRYPTION_KEYS_RETIRED` can sign a job token the app accepts, for any job and user, and an `iat` cutoff wouldn't stop them, because `iat` is part of what they sign. So in a leak the old key never goes in a running service's list: stop the app and worker, move the rows, and start on the new key alone. The app is down for as long as the driver takes, roughly 15 ms a row, and a script still running loses its result.
- [2026-11-05] [Docs] The usual rotation steps no longer stop the worker and wait for running scripts before the key change, because those scripts now carry on through it. Step 5 now also covers them: their tokens stop working when the old key goes at step 6.
