# 2026-11-05

- [2026-11-05] [Security] **One rejected entry can no longer stop the tool audit log.** `AuditLogger.flush` wrote each batch in one insert and put the whole batch back on any failure, so a single entry the database rejected failed every flush after it: nothing more reached `tool_audit_logs` until a restart, which also lost the buffer, and the buffer grew without limit until then. Any failed tool action whose config named no tool did this, because the executor passed `toolId: 0`. So did an event still pointing at a deleted credential, a credential deleted in the seconds before a flush, and a NUL byte in an error message. A missing tool id is now stored as null. A rejected batch is retried one entry at a time, and each entry gives up only what was rejected: a tool id that can't be referenced moves into `action_details`, and contents that still can't be stored leave a row saying who did what and whether it worked, with `action_details.detailsRejected` and the full entry in the server log, secrets masked. Only an entry whose user id can't be stored is dropped, and that is logged the same way. Failures that aren't the entry's fault, such as a refused connection or a missing table, still keep entries for retry, now capped at 1,000: past that the oldest go to the server log. Flush failures also stop logging Drizzle's message, which repeated every value in the batch. `tests/storage/audit-log-flush.test.ts` covers this against real Postgres.
