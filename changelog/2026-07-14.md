# Changelog - 2026-07-14

- [2026-07-15] [Bug Fix] Remote `cronium.output()`/`cronium.input()` no longer fails with `EOF` on the dev stack. After the tunnel-host fix, remote events still failed (`Post "http://127.0.0.1:9090/executions/.../output": EOF`). The runner's tunnel reached the orchestrator, which dialed the runtime at `runtime-api:8089`, but the dev `runtime-api` was actually listening on its default `:8081` — so the dial was refused and the connection closed with no response (EOF). Root causes: (1) the dev compose's `runtime-api` service set **bare** `PORT`/`JWT_SECRET`/`BACKEND_URL`/`VALKEY_URL`, but the runtime loads config through `applyLegacyEnvOverrides` (`RUNTIME_*` names), so those were ignored — it stayed on `:8081` with the default backend URL; rewrote the block to `RUNTIME_PORT=8089` / `RUNTIME_JWT_SECRET` / `RUNTIME_BACKEND_URL` / `RUNTIME_BACKEND_TOKEN` / `RUNTIME_VALKEY_URL` and pointed valkey at the working container name (`cronium-valkey-dev`). (2) `config.go` marked `JWTSecret` `required` at the envconfig layer, but `envconfig.Process()` runs **before** the `RUNTIME_*` overrides, so a config supplying the secret only via `RUNTIME_JWT_SECRET` (the documented/compose var — including the from-source `infra/docker/docker-compose.yml`) fataled with "required key JWT_SECRET missing value"; dropped the redundant tag since `Validate()` already enforces a non-empty secret after overrides. Verified on the running dev stack: runtime boots on `:8089` with only `RUNTIME_JWT_SECRET`, connects to Valkey, serves `/health` 200, and is reachable from the orchestrator container; runtime `go build`/`vet`/`test` clean.

- [2026-07-14] [Bug Fix] Cronium SDK now presents the same interface locally (container) and remotely (runner). Auditing "does the SDK work in both places" surfaced that the runner injects a thinner, differently-named helper set than the container ships, so a script written to the documented interface silently broke when moved between locations: documented **bash** uses `cronium_output` / `cronium_get_variable` (snake, underscore) but the runner only defined `cronium.output` / `cronium.getVariable` (dot, camel) — a documented bash script failed remotely with "command not found"; documented **python** uses `cronium.get_variable` / `cronium.set_variable` (snake) but the runner only defined `getVariable` / `setVariable`. `cronium.input()`/`output()` already matched in python/node, which is why the tested python `output()`→`input()` workflow passed once the tunnel was fixed. Added the documented aliases to the runner's generated discovery scripts (`internal/helpers/discovery.go`: bash underscore forms + python snake_case forms, both exported), routing to the same helper binaries; node already matched. Additive only — existing runner-form scripts keep working. Generated scripts pass python/bash/node syntax checks; runner `go build`/`go vet` clean. Known remaining gap: `set_condition`/`setCondition` has **no** runner helper binary, so a condition set from a remote script is currently a no-op — closing it needs a new `cmd/helpers/setCondition` binary plus embed wiring (reported, not yet built).

- [2026-07-14] [Chore] Drift-locked the container SDK against its canonical source [Unified I/O Phase 6]. `apps/runtime/runtime-helpers/` holds the canonical, documented, tested, publishable SDK (`package.json`/`setup.py`/README/tests), but the execution container images build from `apps/runtime/container-images/<lang>/` and `COPY` a byte-identical mirror of each helper out of that context; nothing builds from `runtime-helpers/` directly, so the two copies could silently diverge and ship a stale helper. Added `scripts/check-sdk-sync.sh` (`--check` default, `--fix` repairs from canonical), a `check:sdk-sync` root script, a dedicated CI `sdk-sync` job that fails on drift, and a README note naming `runtime-helpers/` the source of truth. This completes the Phase 6 SDK consolidation started by deleting the dead SSH inline helper: the previously "three divergent helpers" are now the container SDK and the runner helpers — two legitimate, interface-compatible implementations — with the fragile SSH copy gone and the remaining duplication drift-locked.

- [2026-07-14] [Bug Fix] Remote (runner) execution now passes data between events; also removed the dead pre-runner SSH helper. Running the same 2-event workflow with the downstream event on a remote test server failed at `cronium.input()` with `RuntimeError: ... Get "http://127.0.0.1:9090/executions/.../input": EOF`. Root cause: the orchestrator's SSH reverse tunnel (`internal/executors/ssh/tunnel.go`) dials the shared runtime service, but its host:port defaulted to `runtime-api:8089` in code while the prod/example runtime service is `cronium-runtime:8081` and `RUNTIME_HOST`/`RUNTIME_PORT` were unset on the orchestrator — so `net.Dial` failed and the tunnel closed the runner's connection with no HTTP response (which the runner's HTTP client reports as EOF). Fixed the code defaults to `cronium-runtime:8081` and set `RUNTIME_HOST`/`RUNTIME_PORT` + `depends_on: cronium-runtime` on the orchestrator in both `infra/docker/docker-compose.yml` and `docker-compose.example.yml`. Also hardened `handleConnection` to half-close each direction (`CloseWrite`) and wait for **both** to drain, so an in-flight response can't be truncated mid-copy. The execution-record creation, `/context` input lookup, and `output`→`scriptOutput` promotion were already intact for the runner path, so this restores cross-location data passing. Phase 6 cleanup: removed `apps/cronium-app/src/lib/ssh/script-executor.ts` — the dead pre-runner SSH inline-helper (zero importers, superseded by the runner's compiled input/output helpers); its siblings `shared.ts`/`terminal.ts` stay (they back the live admin terminal). Verified: orchestrator + runner `go build`/`go vet`, app typecheck. Needs runtime verification in a full deployment (a 2-event workflow with the downstream event on server 6/7).

- [2026-07-14] [Bug Fix] Workflow input fallback for a missing/failed predecessor is now explicit [Unified I/O Phase 5 / M6]. A downstream step whose predecessor produced no output (skipped, failed, or emitted nothing) previously fell through to the trigger's initial input, so a step could silently run on stale/unrelated data. `resolveWorkflowInput` (`lib/unified-io/resolve-input.ts`, a pure, unit-tested extraction of the former inline logic) now returns the trigger input only for a start node, and an explicit empty object `{}` for a downstream step with no usable predecessor output — no silent reach-back to the trigger. Covered by 6 unit cases.

- [2026-07-14] [Feature] Enforce single-predecessor workflows (no fan-in) server-side [Unified I/O Phase 5]. The Unified I/O input channel carries exactly one predecessor's output, so a "fan-in" node with multiple incoming edges has undefined input semantics. Added a `.refine` to both `createWorkflowSchema` and `updateWorkflowSchema` (`shared/schemas/workflows.ts`) rejecting any workflow whose edge set targets the same node more than once, so fan-in configurations are refused at the API boundary rather than silently mis-executing.

- [2026-07-14] [Bug Fix] Unified I/O security + reliability hardening [Phase 4]. (H3) The runtime `/output` route now enforces a 5 MB body cap (413 on exceed) so a runaway `cronium.output()` can't OOM the app. (H4) The output write is an atomic row-locked transaction (`.for("update")`) so concurrent writes to the same execution can't interleave and lose data. (H5) The `/context` route no longer returns the user's email/name (PII); it keeps `userId` only. (L5) Every runtime handler now guards the JWT-claims type assertion and returns 401 instead of panicking on a malformed token. (L6) The audit write runs on a detached context so a cancelled request can't abort it. (M7) The container runtime token's lifetime is now `job timeout + 1h` (was a fixed window that could expire mid-job). (H2) The backend relay rebuilds the request body via `GetBody` on each retry and closes bodies per iteration (previously a retry re-sent an already-consumed body). Verified: runtime `go build`/`go vet`, app typecheck + lint.

- [2026-07-14] [Feature] Tool Action and HTTP Request events now emit output into Unified I/O [Phase 2/3]. Read-type tool actions and HTTP events can now feed downstream workflow steps: `ToolAction` carries a `producesOutput` flag, `executeToolAction`/`executeHttpEvent` return it, and `runInProcessJob` promotes the returned data to `job.result.scriptOutput` (the field workflow chaining reads) only when the action succeeded and is marked output-producing. This is the prerequisite for the planned SQL Tool integration (read queries → Unified I/O). Also gated all Unified I/O diagnostic tracing behind `CRONIUM_UNIFIED_IO_DEBUG` via a small `lib/unified-io/debug.ts` helper, so the chain is quiet by default.

- [2026-07-14] [Refactor] Deduplicated the Unified I/O output/condition extractor and deleted dead code [Phase 2]. The logic that reads `scriptOutput`/`condition` off a completed job existed in two places that had already drifted; consolidated into a single `extractScriptOutputAndCondition` helper in `job-polling-service.ts`. Removed the dead `workflow-job-monitor` (superseded by the polling service).

- [2026-07-14] [Bug Fix] Unified I/O Phase 1 — local container execution now passes data between events. Fixes the stack of bugs that made `cronium.output()`/`cronium.input()` fail on the default container path (a Python workflow event failed with `NameError: name 'cronium' is not defined`). (C0) The orchestrator ran the raw user script (`python -c <content>`) with no helper loaded, though the docs/runner assume no-import usage; `buildCommand` now prepends the loader per language (`import cronium` / `globalThis.cronium = require('cronium')` / `source cronium.sh`) so `cronium` is available without an explicit import. (C1) The runtime execution token's JWT claim was `jobID` while the container env `CRONIUM_EXECUTION_ID` and the runtime API URL used `exec_<jobID>_<ts>`, so every `output()`/`input()` was rejected 403 ("execution ID mismatch"); worse, one `tokens` map held both the executionID and the JWT and clobbered itself, so `CRONIUM_EXECUTION_ID` ended up as the token. Split into separate `executionIDs`/`tokens` maps and set the JWT claim to the real executionID. (C2/C3) The job-complete route rebuilt `job.result` from scratch and `updateJobStatus` replaces it, destroying data a script published via `cronium.output()` (which the runtime `/output` route stores on `job.result.output`); the completion route now reads that stored output and promotes it to `job.result.scriptOutput` — the one field workflow chaining reads. (L1) The poller's `result.output.data` fallback assumed a nested `.data` wrapper the `/output` route never writes; it now reads `result.output` directly. (M3) Workflow chaining dropped scalar outputs (`cronium.output("x")` became `{}`); scalars are now wrapped (`{ value }`) so they survive the object-typed input channel while objects/arrays pass through unchanged. Verified: orchestrator `go build`/`go vet`, app typecheck + lint + production build. NOTE: this covers **local container** execution (the SDK → runtime-sidecar path). Remote execution via the cronium-runner agent still discards its `output.json` and the orchestrator never forwards `scriptOutput` — cross-location data passing is the next slice (not yet wired); runtime end-to-end verification of the container path needs the full Docker stack.

- [2026-07-14] [Bug Fix] HTTP Request events now execute (the follow-up flagged after the Tool Action fix). Like tool actions, `HTTP_REQUEST` events have no script, so they were dispatched to the orchestrator as scriptless container jobs and failed with "container job missing script configuration" (the app's `executeHttpRequest` engine existed but had zero callers). Fixed with the same in-process approach: a new `lib/scheduler/http-event-executor.ts` (`executeHttpEvent`) interpolates `${cronium.input.*}` / user variables into the URL, body, and header values, runs the request via the existing axios executor, and returns a normalized result; `in-process-executor.ts` now dispatches `HTTP_REQUEST` jobs to it and `TOOL_ACTION` jobs to `executeToolAction`. `jobService.claimJobs` also excludes `HTTP_REQUEST`, and HTTP jobs are built with `retries: 0`, matching the tool-action handling. Self-hosted note: HTTP events call user-configured URLs and (unlike host-allowlisted tool webhooks) are intentionally unrestricted, so legitimate internal endpoints keep working — acceptable under the single-tenant/operator-is-author model. Resolves the second deferred item; the first deferred item — a Go orchestrator tool executor / `cronium/tool-executor:latest` image — is confirmed unnecessary, since both scriptless event types now run in-process (all tools are outbound HTTPS/SMTP). Tests: `executeHttpEvent` result mapping (no-URL / 2xx / 4xx / transport error) and the HTTP dispatch branch of `runInProcessJob`; suite 82 passing across 11 files.

- [2026-07-14] [Bug Fix] Tool Action events now execute. Standalone `TOOL_ACTION` events (Run button, scheduled, and workflow steps) were dispatched to the Go orchestrator, which only has `container`/`ssh` executors: `job-transformer.ts` mapped a tool-action job to a scriptless `container` job, so every run failed with the orchestrator's "container job missing script configuration" (e.g. event 576's Slack send). The app already has a working, hardened in-process tool engine (`executeToolAction`: SSRF guard, single-attempt retry, circuit breaker, secret redaction) but it was only reached for conditional actions and the manual test button. Fix (in-process execution, per `_plans/tool-event-audit.md` Option A): a new `lib/scheduler/in-process-executor.ts` runs `TOOL_ACTION` jobs in-process and reports the result through `jobService.updateJobStatus` — the same completion path the orchestrator callback uses (log finalize + WebSocket broadcast + conditional-action hooks) — so the `jobs`/`logs` records, the UI, and workflow job-polling all keep working unchanged. Wired into the three job-creation sites (`events.execute`, `scheduler.executeScript`, `scheduler.executeEvent`); `jobService.claimJobs` now excludes `TOOL_ACTION` so the orchestrator can never claim one; and tool-action jobs are built with `retries: 0` (they are non-idempotent — a FAILED status must finalize, not re-queue into a stuck state). No Go tool executor or `cronium/tool-executor:latest` image is needed (all tools are outbound HTTPS/SMTP). HTTP_REQUEST events remain broken the same way and are noted for a follow-up.

- [2026-07-14] [Bug Fix] Made `events.toolActionConfig` parsing robust and consistent. The form saves the config as a `JSON.stringify` string into a `jsonb` column (double-encoding), so readers disagreed: the edit form assumed a string, `job-payload-builder` assumed an object (yielding `toolType: "unknown"`), and `executeToolAction` handled both inconsistently. Added a shared `lib/tools/tool-action-config.ts` `parseToolActionConfig` (handles object, JSON string, and double-encoded string) and repointed the edit-form loader, the payload builder, and the executor at it. The edit form now restores the tool/action/parameters whether the stored config is a string or an object, removing a latent break where an object-shaped config would render the form empty and block re-save. Storage format is unchanged (readers are now tolerant) to avoid a data migration.
