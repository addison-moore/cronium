# Changelog - 2026-07-14

- [2026-07-14] [Bug Fix] Tool Action events now execute. Standalone `TOOL_ACTION` events (Run button, scheduled, and workflow steps) were dispatched to the Go orchestrator, which only has `container`/`ssh` executors: `job-transformer.ts` mapped a tool-action job to a scriptless `container` job, so every run failed with the orchestrator's "container job missing script configuration" (e.g. event 576's Slack send). The app already has a working, hardened in-process tool engine (`executeToolAction`: SSRF guard, single-attempt retry, circuit breaker, secret redaction) but it was only reached for conditional actions and the manual test button. Fix (in-process execution, per `_plans/tool-event-audit.md` Option A): a new `lib/scheduler/in-process-executor.ts` runs `TOOL_ACTION` jobs in-process and reports the result through `jobService.updateJobStatus` — the same completion path the orchestrator callback uses (log finalize + WebSocket broadcast + conditional-action hooks) — so the `jobs`/`logs` records, the UI, and workflow job-polling all keep working unchanged. Wired into the three job-creation sites (`events.execute`, `scheduler.executeScript`, `scheduler.executeEvent`); `jobService.claimJobs` now excludes `TOOL_ACTION` so the orchestrator can never claim one; and tool-action jobs are built with `retries: 0` (they are non-idempotent — a FAILED status must finalize, not re-queue into a stuck state). No Go tool executor or `cronium/tool-executor:latest` image is needed (all tools are outbound HTTPS/SMTP). HTTP_REQUEST events remain broken the same way and are noted for a follow-up.

- [2026-07-14] [Bug Fix] Made `events.toolActionConfig` parsing robust and consistent. The form saves the config as a `JSON.stringify` string into a `jsonb` column (double-encoding), so readers disagreed: the edit form assumed a string, `job-payload-builder` assumed an object (yielding `toolType: "unknown"`), and `executeToolAction` handled both inconsistently. Added a shared `lib/tools/tool-action-config.ts` `parseToolActionConfig` (handles object, JSON string, and double-encoded string) and repointed the edit-form loader, the payload builder, and the executor at it. The edit form now restores the tool/action/parameters whether the stored config is a string or an object, removing a latent break where an object-shaped config would render the form empty and block re-save. Storage format is unchanged (readers are now tolerant) to avoid a data migration.

- [2026-07-14] [Testing] Added unit tests: `runInProcessJob`/`isInProcessJobType` (COMPLETED on success, FAILED on a failure result, and FAILED-finalized without throwing when the engine throws) and `parseToolActionConfig` (object / JSON string / double-encoded / malformed → null). Suite: 77 passing across 10 files.
